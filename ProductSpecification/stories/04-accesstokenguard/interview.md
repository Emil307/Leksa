# Story 04 — AccessTokenGuard: контекст интервью

Защита продуктовых ручек единым access JWT. В этой истории guard впервые
используется на тонкой ручке, которая возвращает текущему пользователю его запись
из `auth.t_users`.

## Scope

**В скоупе:**

- Общий guard для продуктовых API-ручек, принимающий access JWT из
  `Authorization: Bearer <token>`.
- Бинарный результат проверки: токен либо полностью корректен и запрос проходит,
  либо ответ всегда одинаковый `401`.
- Проверка подписи JWT и обязательных claims `sub`, `sid`, `exp`, `aud`, `jti`.
- Проверка активной сессии в PostgreSQL на каждом защищённом запросе.
- `GET /api/v1/profile` как первая защищённая ручка.
- Ответ профиля содержит все поля строки `auth.t_users`, а имена полей API
  записываются в camelCase.

**Вне скоупа:**

- Выпуск access- и refresh-токенов.
- Обновление и ротация токенов.
- Logout и операции отзыва сессии.
- Роли, permissions и разграничение доступа после аутентификации.
- Rate limiting.
- `learner.t_profiles`, онбординг и автоматическое создание learner-профиля.
- Redis read model активных сессий и любой in-memory-кеш.

## API Endpoints

| Метод | Путь | Статус |
|---|---|---|
| GET | `/api/v1/profile` | NOT YET IMPLEMENTED |

Ручка не принимает идентификатор пользователя. Пользователь определяется только
из проверенного access JWT.

Успешный ответ возвращает всю запись `auth.t_users`:

```json
{
  "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "name": "",
  "surname": null,
  "email": "user@example.com",
  "isSuperuser": false,
  "createdAt": "2026-08-14T10:00:00Z",
  "updatedAt": null,
  "avatarId": null,
  "birthday": null,
  "gender": null,
  "city": null,
  "phone": null
}
```

Значения не дополняются данными из `learner.t_profiles` и не вычисляются на лету.
Nullable-колонки остаются `null`.

## Token / Auth Requirements

- Схема заголовка — `Authorization: Bearer <token>`.
- Алгоритм подписи — JWT HS256, секрет берётся из конфигурации и не имеет
  рабочего значения по умолчанию.
- `sub` — UUID пользователя из `auth.t_users.id`.
- `sid` — UUID сессии из `auth.t_sessions.id`.
- `exp` — срок действия access-токена в Unix timestamp.
- `aud` — строго `uwords-api` для frontend и Telegram-бота.
- `jti` — уникальный UUID конкретного access-токена.

`jti` в этой истории проверяется на наличие и корректный формат. Отдельного
denylist для него нет: отзыв обеспечивается состоянием сессии.

## Key Architectural Decisions

DECISION: guard не ограничивается криптографической проверкой JWT. На каждом
защищённом запросе он читает `auth.t_sessions` и пропускает запрос, только если
сессия существует, принадлежит пользователю из `sub` и её `expires_at` ещё не
наступил.

DECISION: состояние сессий не кешируется в памяти — backend работает в нескольких
инстансах. Пока чтение идёт напрямую из PostgreSQL. Если это станет проблемой,
можно отдельно добавить read model активных сессий в Redis; текущая история её не
проектирует и не создаёт.

DECISION: `aud` одинаков для всех внешних клиентов и обозначает получателя токена —
`uwords-api`. Различать frontend и bot через `aud` не нужно.

DECISION: `GET /api/v1/profile` возвращает только строку `auth.t_users`, но
адаптирует snake_case имена колонок к camelCase API. Ручка не знает о
`learner.t_profiles`.

DECISION: история самостоятельна и не ждёт завершения EmailCodeLogin или
SessionRenewal. Она согласует JWT-контракт с ними, но должна доставить guard и
профильную ручку независимо.

## Business Rules & Constraints

- Корректным считается только токен, который одновременно прошёл проверку HS256,
  содержит все обязательные claims правильного типа, не истёк, имеет
  `aud = "uwords-api"` и ссылается на активную сессию своего пользователя.
- Отсутствующий заголовок, неверная Bearer-схема, повреждённый JWT, неверная
  подпись или алгоритм, отсутствующий или некорректный claim, истёкший токен,
  другое `aud`, отсутствующая или истёкшая сессия и несовпадение `sid` с `sub`
  не различаются снаружи.
- Любой отказ возвращает HTTP `401` через существующий конверт ошибок:
  `{code: "UNAUTHORIZED", message: "Unauthorized", payload: null}`.
- Ответ не объясняет причину отказа и не создаёт oracle для проверки пользователей,
  сессий или отдельных claims.
- При успешной проверке профиль выбирается по `sub`; клиент не может передать или
  подменить `userId`.
- В профильном ответе нет access token, refresh token или данных сессии.

## Already Implemented (REUSE)

- `domain.errors` и централизованный `register_exception_handlers` уже дают
  `UNAUTHORIZED` и единый конверт ошибок; новый механизм ошибок не нужен.
- `adapter_storage` содержит базовую SQLAlchemy-инфраструктуру, `UnitOfWork` и
  основу repositories.
- `application` использует ручной wiring и router factory; guard и профильная
  ручка должны встроиться в эту схему.
- `docs/db-schema.sql` описывает поля `auth.t_users` и связь с
  `auth.t_sessions`, но это пока документация, а не реализованные ORM-модели.
- Story 1 закрепила HS256, `sub`, `sid` и `exp`; ADR задачи 1 добавил единый
  клиентский контракт, `aud` и `jti`.
- В acceptance-сьюте сейчас включён только `TestHealthAcceptance`; защищённых
  продуктовых ручек ещё нет.

## NOT Yet Implemented (Gaps)

- JWT decoder/validator и обязательная библиотека подписи.
- Auth context, который guard передаёт защищённой ручке после проверки.
- Порт чтения активной сессии и пользователя.
- ORM-модели и storage repositories для `auth.t_sessions` и `auth.t_users`, если
  они не появятся в коде раньше этой истории.
- Guard/dependency на REST-границе.
- Usecase чтения текущего пользователя.
- Pydantic response schema со всеми полями `auth.t_users` и camelCase aliases.
- Router `GET /api/v1/profile` и его wiring в приложение.
- Unit-, adapter- и acceptance-тесты для успешного профиля и единого `401`.

## Cross-Story Dependencies

- История не имеет блокирующей зависимости и реализуется самостоятельно.
- Контракт должен оставаться совместимым с access JWT из EmailCodeLogin и общим
  клиентским JWT-решением из ADR задачи 1.
- SessionRenewal в будущем выпускает новый access JWT с теми же обязательными
  claims; guard от способа выпуска токена не зависит.
- Будущий logout/revocation сможет немедленно закрыть доступ удалением или
  деактивацией сессии, но сами эти операции находятся вне текущего scope.

## Testing Considerations

- Один положительный acceptance-сценарий получает весь `auth.t_users` в camelCase
  по корректному access JWT.
- Все отрицательные варианты утверждают один и тот же точный статус и конверт
  `401`, без различающихся сообщений.
- Отдельно проверяются: отсутствие заголовка, неверная схема, повреждённый токен,
  неверная подпись, другой алгоритм, отсутствие каждого обязательного claim,
  неверные типы и UUID, истёкший `exp`, чужой `aud`, неизвестный `sid`, истёкшая
  сессия и сессия другого `sub`.
- Проверяется, что `userId` из query/body не может выбрать чужой профиль; ручка
  вообще не принимает такой параметр.
- Проверки времени используют управляемые часы, а не реальное ожидание.
- Проверка активной сессии должна выполняться через общее хранилище, чтобы тесты
  не закрепили in-memory состояние.

## Performance / Rate Limits

- `ProductSpecification/ExpectedLoad.md` пока не содержит численных ограничений.
- Каждый защищённый запрос делает чтение активной сессии из PostgreSQL. Этот
  компромисс принят осознанно ради немедленного отзыва и согласованности между
  инстансами.
- Redis read model рассматривается только как будущая оптимизация после измеренной
  проблемы; заранее в эту историю не добавляется.
