# AccessTokenGuard — Security-тесты

> **Implementation Order**: Tests are numbered for sequential TDD implementation.
> Сначала ограничивается входная граница JWT, затем проверяются подпись, claims и
> актуальность сессии, после чего закрепляются ownership, безопасный вывод и
> нераскрывающая диагностика.

---

## 1. Граница заголовка

### 1.1 Лимит Authorization считается по wire bytes до разбора JWT

Tier: 2 (hz-01, hz-06, sec:InputLength)

```gherkin
Дано существует пользователь с действующей сессией
Когда клиент запрашивает профиль с заголовком авторизации длиной <длина>
Тогда запрос имеет исход <исход>
И заголовок за границей отклоняется до проверки сессии
```

| длина | исход |
|---|---|
| ровно разрешённая граница wire bytes и корректный токен | профиль возвращён |
| на один wire byte больше разрешённой границы | единый отказ авторизации |
| многобайтные символы с числом code points ниже границы, но wire bytes выше | единый отказ авторизации |

---

## 2. JWT и сессия

### 2.1 Сервер принимает только доверенный HS256 JWT

Tier: 2 (hz-05, sec:JWT)

```gherkin
Дано существует пользователь с действующей сессией
Когда клиент запрашивает профиль с вариантом токена <вариант>
Тогда запрос имеет исход <исход>
И отказ дословно совпадает с единым отказом авторизации
```

| вариант | исход |
|---|---|
| JWT с корректной HS256-подписью серверным секретом | профиль возвращён |
| JWT с изменённой подписью | запрос отклонён |
| JWT с подписью другим секретом | запрос отклонён |
| JWT с другим алгоритмом | запрос отклонён |
| JWT без алгоритма подписи | запрос отклонён |

---

### 2.2 Каждый обязательный claim проверяется без неявных преобразований

Tier: 2 (hz-05, sec:JWT)

```gherkin
Дано существует пользователь с действующей сессией
Когда клиент запрашивает профиль с вариантом claims <вариант>
Тогда запрос отклоняется как неудачная авторизация
И ответ дословно совпадает с единым отказом авторизации
И значение не приводится к другому типу молча
```

| вариант |
|---|
| отсутствует один из sub, sid, jti, exp, aud |
| sub, sid или jti не является строковым UUID |
| exp не является целым числом |
| aud не является строкой |
| aud отличается регистром или значением от uwords-api |

---

### 2.3 Обе границы истечения используют одни управляемые часы

Tier: 2 (hz-01, hz-04, hz-07, sec:JWT)

```gherkin
Дано пользователь имеет корректный access-токен и связанную с ним сессию
Когда срок <граница> имеет случай <случай>
Тогда запрос имеет исход <исход>
```

| граница | случай | исход |
|---|---|---|
| срок access-токена | за одну секунду до | профиль возвращён |
| срок access-токена | точно в момент | единый отказ авторизации |
| срок access-токена | через одну секунду после | единый отказ авторизации |
| срок access-токена | значение равно нулю или отрицательно | единый отказ авторизации |
| срок access-токена | значение равно 253402300800 или больше | единый отказ авторизации |
| срок access-токена | значение больше точного целого числа JavaScript | единый отказ авторизации |
| срок сессии | за одну микросекунду до | профиль возвращён |
| срок сессии | точно в момент | единый отказ авторизации |
| срок сессии | через одну микросекунду после | единый отказ авторизации |

---

### 2.4 Решение о сессии перечитывается на каждом запросе и каждом инстансе

Tier: 2 (hz-03, hz-04, sec:JWT)

```gherkin
Дано один и тот же access-токен успешно прошёл через каждый из двух инстансов приложения
Когда сессия становится неактивной в PostgreSQL
И токен повторно предъявляется каждому уже прогретому инстансу
Тогда каждый повторный запрос отклоняется как неудачная авторизация
И ни одно прежнее положительное решение не разрешает доступ
```

## 3. Ownership и безопасный вывод

### 3.1 Запрос профиля возвращает безопасно сериализованные данные владельца токена

Tier: 2 (hz-05, hz-07, sec:IDOR, sec:XSS)

```gherkin
Дано два пользователя имеют разные учётные записи и действующие сессии
И текстовые поля учётной записи первого пользователя содержат HTML, SQL, перевод строки и управляющие метасимволы
И первый пользователь предъявляет свой корректный access-токен
Когда первый пользователь запрашивает профиль с чужим существующим и несуществующим идентификаторами
Тогда оба ответа дословно совпадают
И оба ответа содержат только учётную запись первого пользователя
И существование и данные второго пользователя не раскрываются
И каждый ответ остаётся одним валидным JSON-документом
И каждое опасное значение возвращено как строковые данные
И значение не создаёт новый заголовок, поле JSON, запрос или строку лога
```

---

## 4. Fail-closed и раскрытие данных

### 4.1 Каждый auth-отказ диагностируется безопасно и закрывает доступ к профилю

Tier: 2 (hz-02, hz-05, hz-07, sec:JWT)

```gherkin
Дано токен, refresh-токен, секрет подписи и персональные данные имеют узнаваемые метки с переводом строки и управляющими символами
И пользователь имеет действующую сессию и корректный access-токен
Когда возникает auth-отказ вида <вид>
Тогда клиент получает дословно единый отказ авторизации
И ответ, сериализованная ошибка и логи содержат фиксированную метку редактирования вместо секретов и персональных данных
И ответ не содержит внутренних деталей приложения
И лог содержит безопасную причину и идентификатор корреляции
И метасимволы не создают новую или поддельную строку лога
И запрос отклоняется как неудачная авторизация
И профиль не возвращается
И безопасный сигнал отказа записан один раз
```

| вид |
|---|
| заголовок не разбирается |
| подпись не проверяется |
| claims не проходят проверку |
| сессия неизвестна, чужая или истекла |
| хранилище сессий недоступно |
| чтение активной сессии завершается ошибкой базы данных |
| чтение активной сессии превышает допустимое время |
| чтение учётной записи пользователя завершается ошибкой базы данных |
| чтение учётной записи пользователя превышает допустимое время |
| учётная запись пользователя не найдена после успешной проверки сессии |

---

### 4.2 Успешный запрос не создаёт сигнал auth-отказа

Tier: 2 (hz-07, sec:JWT)

```gherkin
Дано пользователь имеет действующую сессию и корректный access-токен
Когда пользователь запрашивает свой профиль
Тогда запрос успешно выполнен
И сигнал auth-отказа не записан
И токен и персональные данные не записаны в журнал
```

---

### 4.3 Отсутствующий или пустой секрет подписи ломает старт

Tier: 2 (hz-05, hz-07, sec:JWT)

```gherkin
Дано секрет подписи access-токена имеет значение <значение>
Когда приложение запускается
Тогда запуск завершается явной ошибкой конфигурации
И рабочее значение по умолчанию не используется
```

| значение |
|---|
| переменная отсутствует |
| пустая строка |
| строка только из пробельных символов |

## DSL Technical Reference

| DSL Statement | Technical Implementation |
|---|---|
| `разрешённая граница wire bytes` | максимум 4096 октетов заголовка `Authorization` до JWT decode и DB access |
| `доверенный HS256 JWT` | decoder allow-list содержит только `HS256`; алгоритм из header не расширяет allow-list |
| `обязательные claims` | `sub`, `sid`, `jti` — UUID strings; `exp` — integer Unix seconds `1..253402300799`; `aud = "uwords-api"` |
| `единый отказ авторизации` | HTTP 401 и ровно `{"code":"UNAUTHORIZED","message":"Unauthorized","payload":null}` |
| `управляемые часы` | один injectable UTC clock для проверки `exp` и `auth.t_sessions.expires_at` |
| `два инстанса приложения` | два guard instance без общего in-memory state, одно PostgreSQL session storage |
| `сессия становится неактивной` | строка удалена либо `expires_at <= now`; Redis/local cache отсутствуют |
| `фиксированная метка редактирования` | структурное поле credential имеет ровно `[REDACTED]` |
| `внутренние детали приложения` | stack-trace markers, SQL keywords, internal class names, constraint names и filesystem paths |
| `безопасная причина` | bounded auth failure reason-code для parsing/signature/claims/session/storage |
| `идентификатор корреляции` | безопасный correlation id без `sub`, `sid`, JWT или PII |
| `сигнал auth-отказа` | различимый log/metric для каждой failure-ветки; отсутствует на happy path |
| `допустимое время` | bounded connect/read timeout PostgreSQL, после которого guard fail-closed |
