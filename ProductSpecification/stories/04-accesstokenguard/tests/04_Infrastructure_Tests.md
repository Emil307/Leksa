# AccessTokenGuard — Infrastructure-тесты

> **Implementation Order**: Tests are numbered for sequential TDD implementation.
> Сначала схема разворачивается совместимо, затем проверяется жизненный цикл
> соединений и восстановление доступа после возврата PostgreSQL.

---

## 1. Схема сессий

### 1.1 Срок сессии вводится без разрыва смешанного развёртывания

Tier: 2 (hz-04)

```gherkin
Дано новая схема развёрнута рядом с предыдущей версией приложения
Когда старая версия читает и записывает сессии в новой схеме
Тогда её рабочие пути не ломаются
И новая версия принимает сессию с заполненным будущим сроком
И новая версия отклоняет legacy-сессию без срока как неактивную
И backfill изменяет только строки без срока, не затрагивая уже заполненные и соседние строки
И отсутствующий или пустой scope backfill не изменяет ни одной строки
И после заполнения старых строк ограничение срока закрепляется схемой
```

---

### 1.2 Повтор завершённого rollout не меняет достигнутое состояние

Tier: 2 (hz-02, hz-04)

```gherkin
Дано rollout срока сессии уже полностью завершён
Когда тот же rollout запускается повторно
Тогда схема и данные остаются в достигнутом состоянии
И ни одна строка не получает повторный эффект
И рабочие пути старой и новой версий по-прежнему не ломаются
```

---

### 1.3 Сбой backfill откатывается целиком и безопасно повторяется

Tier: 2 (hz-02, hz-04)

```gherkin
Дано несколько legacy-сессий ожидают заполнения срока
Когда последняя запись backfill завершается ошибкой
Тогда все предыдущие изменения этого backfill отсутствуют
И ограничение заполненного срока не устанавливается преждевременно
И повторный запуск после устранения ошибки заполняет каждую целевую строку ровно один раз
И уже заполненные и соседние строки остаются неизменными
```

## 2. Ресурсы PostgreSQL

### 2.1 Проверка сессии освобождает соединение на каждом исходе

Tier: 2 (hz-02, hz-06)

```gherkin
Дано пул соединений PostgreSQL находится на исходном уровне
Когда много запросов профиля завершаются успехом, отказом сессии и ошибкой хранилища
Тогда после каждого исхода число занятых соединений возвращается к исходному уровню
И последующие запросы продолжают получать соединение
```

---

### 2.2 После восстановления PostgreSQL корректный запрос снова проходит

Tier: 2 (hz-02, hz-07)

```gherkin
Дано пользователь имеет действующую сессию и корректный access-токен
И предыдущая проверка сессии завершилась отказом из-за недоступности PostgreSQL
Когда PostgreSQL снова доступен и пользователь повторяет запрос профиля
Тогда запрос успешно выполнен
И возвращается актуальная учётная запись пользователя
И прежний отказ не сохраняется в локальном состоянии приложения
```

## DSL Technical Reference

| DSL Statement | Technical Implementation |
|---|---|
| `новая схема` | additive `auth.t_sessions.expires_at timestamptz NULL`, backfill, затем `NOT NULL` |
| `предыдущая версия приложения` | N-1 read/write paths на N schema |
| `legacy-сессия без срока` | `auth.t_sessions.expires_at IS NULL` → единый HTTP 401 |
| `scope backfill` | только строки `auth.t_sessions.expires_at IS NULL`; пустой набор меняет 0 строк |
| `тот же rollout запускается повторно` | повторное применение additive migration, backfill и constraint step |
| `последняя запись backfill завершается ошибкой` | deterministic failure на последнем UPDATE внутри одной транзакции |
| `пул соединений PostgreSQL` | checked-out connections SQLAlchemy pool |
| `ошибка хранилища` | исключение при чтении `auth.t_sessions` или `auth.t_users` |
| `локальное состояние приложения` | отсутствие correctness-bearing in-memory cache отрицательных или положительных auth-решений |
