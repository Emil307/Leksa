# AccessTokenGuard — API-тесты

> **Implementation Order**: Tests are numbered for sequential TDD implementation.
> Сначала профиль читается по корректному токену, затем закрепляется единый отказ
> для каждой границы guard и, последним, выбор владельца только по токену.

---

## 1. Чтение профиля

### 1.1 Пользователь с действующей сессией получает всю свою запись

Tier: 1

```gherkin
Дано пользователь имеет действующую сессию и корректный access-токен
И в его учётной записи заполнено каждое поле
Когда пользователь запрашивает свой профиль
Тогда запрос успешно выполнен
И ответ содержит все поля его учётной записи в клиентских именах
И значения ответа точно совпадают с сохранённой записью
И ответ не обёрнут во внешний конверт
И в ответе нет данных сессии, токенов и учебного профиля
```

---

### 1.2 Nullable-поля, Unicode и даты возвращаются без подмены

Tier: 2 (hz-01, hz-07)

```gherkin
Дано пользователь имеет действующую сессию и корректный access-токен
И nullable-поля его учётной записи не заполнены
И текстовые поля содержат многобайтный текст, комбинируемые символы и метасимволы
Когда пользователь запрашивает свой профиль
Тогда запрос успешно выполнен
И каждое незаполненное поле представлено как null
И precomposed и combining-form текст возвращены byte-exact относительно хранения без нормализации на чтении
И ответ остаётся валидным UTF-8 JSON
И при враждебных locale и timezone моменты времени представлены в UTC, а день рождения — календарной датой
```

## 2. Единый отказ авторизации

### 2.1 Запрос профиля с невалидной авторизацией отклоняется единообразно

Tier: 2 (hz-02, hz-04, hz-05)

```gherkin
Дано существует пользователь с действующей сессией
И access-токен корректно подписан и не истёк
Когда клиент запрашивает профиль с вариантом авторизации <вид>
Тогда запрос отклоняется как неудачная авторизация
И ответ дословно совпадает с единым отказом авторизации
И профиль пользователя не возвращается
```

| вид |
|---|
| заголовок отсутствует |
| заголовок пуст |
| указана другая схема |
| после Bearer нет токена |
| после Bearer указано больше одного значения |
| заголовок длиннее разрешённой границы |
| токен не имеет структуры JWT |
| подпись токена изменена |
| токен подписан другим секретом |
| токен объявляет другой алгоритм |
| токен не содержит один из обязательных claims |
| обязательный claim имеет неверный тип или формат |
| audience отличается от получателя API |
| срок действия токена уже наступил |
| сессия никогда не существовала |
| сессия принадлежит другому пользователю |
| срок сессии уже наступил |
| срок legacy-сессии не заполнен |
| чтение сессии невозможно |
| чтение учётной записи невозможно |

## 3. Выбор владельца

### 3.1 Клиентское значение userId не может выбрать чужой профиль

Tier: 2 (hz-05)

```gherkin
Дано два пользователя имеют разные учётные записи и действующие сессии
И первый пользователь предъявляет свой корректный access-токен
Когда первый пользователь запрашивает профиль и передаёт идентификатор второго
Тогда запрос успешно выполнен
И ответ содержит только учётную запись первого пользователя
И данные второго пользователя не возвращаются
```

## 4. Опубликованный контракт

### 4.1 Опубликованный контракт описывает чтение профиля как защищённое

Tier: 2 (review: stage-3 1.1)

```gherkin
Дано приложение запущено
Когда клиент запрашивает опубликованный контракт API
Тогда контракт объявляет схему авторизации Bearer с форматом JWT
И операция чтения профиля требует эту схему
И операция объявляет и успешный ответ, и единый отказ авторизации
И ни один незащищённый вариант чтения профиля не объявлен
```

## DSL Technical Reference

| DSL Statement | Technical Implementation |
|---|---|
| `корректный access-токен` | JWT HS256 с UUID `sub`, `sid`, `jti`, целым `exp` и `aud = "uwords-api"` |
| `действующая сессия` | `auth.t_sessions.id = sid`, `user_id = sub`, `expires_at > now` |
| `пользователь запрашивает свой профиль` | `GET /api/v1/profile` с `Authorization: Bearer <JWT>` |
| `все поля его учётной записи в клиентских именах` | `id`, `name`, `surname`, `email`, `isSuperuser`, `createdAt`, `updatedAt`, `avatarId`, `birthday`, `gender`, `city`, `phone` |
| `запрос успешно выполнен` | HTTP 200, корневой JSON-объект `UserProfile` |
| `единый отказ авторизации` | HTTP 401 и ровно `{"code":"UNAUTHORIZED","message":"Unauthorized","payload":null}` |
| `разрешённая граница` | длина `Authorization` не более 4096 wire bytes |
| `обязательные claims` | `sub`, `sid`, `exp`, `aud`, `jti` |
| `срок токена уже наступил` | внедряемые часы дают `now >= exp` |
| `срок сессии уже наступил` | те же внедряемые часы дают `now >= auth.t_sessions.expires_at` |
| `идентификатор второго` | непризнанный контрактом query-параметр `userId=<other-user-id>` |
| `опубликованный контракт API` | `GET /openapi.json` |
| `схема авторизации Bearer с форматом JWT` | `components.securitySchemes.bearerAuth` = `{type: http, scheme: bearer, bearerFormat: JWT}` |
| `операция чтения профиля` | `paths./api/v1/profile.get` |
| `требует эту схему` | `security` операции содержит `bearerAuth` |
| `успешный ответ и единый отказ авторизации` | ключи `responses` — ровно `200` и `401` |
