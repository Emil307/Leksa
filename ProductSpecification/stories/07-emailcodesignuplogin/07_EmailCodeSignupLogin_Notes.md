# Регистрация и вход по коду из письма в приложении — Notes

Источник решений: `interview.md` в этой папке. Здесь — только то, чего нет в основной
спецификации: механика, предупреждения, техника.

## Warnings

### Functional

- Ответ `verify` не сообщает, новый это пользователь или существующий, — фронт не должен
  пытаться это вычислить (например, запросом профиля). Один поток — сознательное решение.
- Любой `401` на `verify` (неверный код / истёк / попытки исчерпаны) отличается только
  полем `message`; фронт его не читает и не различает причины. Одно сообщение на все три.
- Бэкенд обесценивает прежний код при повторном `challenge/start`; фронт после повторной
  отправки обязан заменить `challengeId` и `expiresAt` на новые и сбросить введённый код.
- Потеря `challengeId` при перезагрузке страницы — принятое ограничение (история 01):
  пользователь возвращается на экран почты и упирается в кулдаун 60 с.

### UI/UX

- Только мобильная раскладка: bottom sheet по `ProductSpecification/ui/ui-conventions.md`
  и `ui/templates/auth-layout.html`; на широком экране панель просто центрируется.
- На экране одна первичная кнопка; «Отправить новый код» и «Изменить адрес» — вторичные.
- Тексты нейтральны: «Войти или создать аккаунт», а не две точки входа.
- Токены, `session.id`, `challengeId` на экран не выводятся ни в одном состоянии.
- Текст `message` из конверта ошибки не показывается; формулировки — свои, по `code` и
  HTTP-статусу.

### Technical

- Приложение открывается Telegram как обычная веб-страница: Telegram WebApp SDK
  (`window.Telegram.WebApp`, `initData`, `MainButton`, тема) не подключается. В Chrome
  для Selenium страница ведёт себя так же, как внутри Telegram.
- Сессия живёт только в памяти React-приложения; `localStorage`, cookie и Telegram
  CloudStorage не используются. Именно поэтому повторное открытие — новый вход.
- `POST /api/v1/auth/token/refresh` не вызывается (история 05 ещё RED); защищённые
  эндпоинты в этой истории не вызываются вообще.
- Код передаётся строкой (`code: "012345"`), не числом — ведущий ноль значим.

## Technical Notes

### Implementation Decisions

- Вызовы: `POST /api/v1/auth/challenge/start` с `{email, challengeType: "EMAIL_CODE"}` →
  `{challengeId, challengeType, expiresAt}`; `POST /api/v1/auth/challenge/verify` с
  `{challengeId, code}` → `{user{id}, session{id, accessToken, refreshToken}}`.
  Контракты — `ProductSpecification/api-specs/`, ничего в бэкенде не меняется.
- Маппинг ошибок (конверт `{code, message, payload}`):
  - `start` 400 `VALIDATION_FAILED` → «Проверьте адрес», остаёмся на экране почты;
  - `start` 409 `CONFLICT` → отсчёт кулдауна перезапускается от `payload.retryAfterSeconds`
    (на экране почты кнопка блокируется на это время; на экране кода — кнопка повтора);
  - `verify` 401 `UNAUTHORIZED` (любое `message`) → одно сообщение, поле открыто;
  - `verify` 400 → трактуется как неподходящий код (на фронте недостижимо при 6 цифрах);
  - 503 `UNAVAILABLE` на любом шаге → «Сервис временно недоступен, попробуйте позже»,
    действие можно повторить.
- Обратный отсчёт до `expiresAt` — локальный таймер по часам клиента; по нулю поле кода
  блокируется, активна только повторная отправка. Это единственное решение, которое фронт
  принимает сам, остальное — ответы API.
- Кулдаун повторной отправки фронт узнаёт только из `409`: ответ `start` длительность паузы
  не сообщает, а бэкенд-константы (`AUTH_CHALLENGE_TTL_SECONDS=300`,
  `AUTH_CHALLENGE_RESEND_COOLDOWN_SECONDS=60`) в фронт не зашиваются. Поэтому после `start`
  кнопка повтора открыта; нажатие внутри паузы даёт `409`, и кнопка закрывается на
  `payload.retryAfterSeconds`. Сообщение при этом одно: «Новый код можно запросить через N с».
- Структура во `frontend/`: страницы `src/pages/{Name}Page.tsx`, фича
  `src/features/auth/{components,logic,__tests__}/`, API-клиент с маппингом конверта.
  Роутинг во `frontend/` ещё не заведён — появится в этой истории.
- Состояния экрана кода: `waiting` (отсчёт идёт) → `submitting` → `rejected` /
  `signed-in`; `expired` (поле закрыто) — только по таймеру; `resend-cooldown` — независимый
  флаг кнопки повтора.

### Load Considerations

- Нагрузка на бэкенд не меняется: те же два эндпоинта, что у истории 01. Защита от
  двойного нажатия убирает дублирующие `start`/`verify`.

### Security Considerations

- Public client: секретов у фронта нет, токены не показываются и в этой истории не
  отправляются. Причины отказа `verify` не разглашаются ни бэкендом, ни экраном.
- Email на экране кода показывается как введён — это адрес самого пользователя.

### Infrastructure

- Selenium E2E (`frontend/e2e/`, Gradle, JUnit 5) идёт против **стаба API** внутри
  `frontend/e2e/` (WireMock или JDK HTTP-сервер); бэкенд и MailHog не поднимаются. Порт
  стаба — из `frontend/infrastructure/.env`; dev-сервер для E2E стартует с `VITE_API_URL`
  на стаб. Стаб держит состояние по email (каждый тест — уникальный адрес), код
  детерминирован, `expiresAt`/`retryAfterSeconds` отдаёт как прод (300 с / 60 с).
- Тесты ждут реальные интервалы и выполняются **параллельно** (JUnit Platform
  `junit.jupiter.execution.parallel.*`, один WebDriver на тест). Открытый вариант на случай
  нехватки параллели: стаб отдаёт укороченные `expiresAt`/`retryAfterSeconds` отдельным
  тестам — без изменений во фронте.
- Юнит-лейн: Vitest 3 + MSW 2, таймер и кулдаун — `vi.useFakeTimers`, реальных ожиданий нет.
- Точность акцепта на реальном контракте остаётся за acceptance-сьютом бэкенда
  (`acceptance/tests/backend/auth/`).

### Integration Points

- История 01 (бэкенд challenge) — потребитель, ничего не меняем.
- История 04 (`GET /profile`) и 05 (`refresh`) — не вызываются.
- История 06 (Telegram-вход) и будущая история хранения сессии — расширят этот же экран
  и это же состояние сессии.
