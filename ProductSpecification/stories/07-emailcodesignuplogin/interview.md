# Story 07: Регистрация и вход по коду из письма в приложении — интервью

Дата: 2026-09-14

## Scope

Клиент этой истории — **Telegram Mini App**, то есть React-приложение из `frontend/`,
которое Telegram открывает внутри себя. Это не сайт (`design/site/` — про тест уровня)
и не бот.

Почему email внутри Telegram, где человек и так опознан: **email — единый аккаунт**
между сайтом, Mini App и ботом. Это постоянное решение, а не временная заглушка до
истории 06 (Telegram-вход). Пользователь привязывает почту, чтобы аккаунт не зависел
от Telegram.

Один поток, без различия «регистрация» и «вход». Пользователь вводит почту, получает
код, вводит код — и оказывается внутри. Новый он или уже был — незаметно и на экране
не различается (бэкенд в ответе `verify` этого и не сообщает, менять API не нужно).

В scope:

- **Экран ввода email** — ввод адреса, отправка `challenge/start`, переход к вводу кода.
  Ошибки: невалидный адрес (400), сервис недоступен (503), кулдаун ещё взведён (409 с
  `retryAfterSeconds`).
- **Экран ввода кода** — 6 цифр, обратный отсчёт до `expiresAt`, кнопка «Отправить
  новый код» с кулдауном, ошибка при 401, блокировка поля по истечении таймера.
- **Сессия и вход в продукт после `verify`** — ответ `verify` принят, приложение
  переходит на экран «после входа».

Вне scope (явно):

- **Хранение сессии между открытиями.** Пока никуда не сохраняем: токены живут только в
  памяти приложения, повторное открытие Mini App — новый вход. Отдельная история, когда
  определимся с local/CloudStorage.
- **Автообновление сессии по refresh-токену** (`POST /api/v1/auth/token/refresh`) —
  бэкенд истории 05 ещё RED, фронт его не трогает.
- **Продуктовый экран после входа.** Продуктовых экранов во `frontend/` нет; после
  `verify` — пустая заглушка без запроса профиля (`GET /api/v1/profile` не вызываем).
- **Telegram WebApp SDK** (`window.Telegram.WebApp`: `ready`, `expand`, тема,
  `MainButton`) — не подключаем. Приложение — обычная веб-страница, которую Telegram
  просто открывает; в Chrome для Selenium она ведёт себя точно так же.
- **Десктопная раскладка.** Только мобильная (bottom sheet из `ui-conventions.md`); на
  широком экране панель просто центрируется.
- Разные точки входа «Войти» / «Создать аккаунт», онбординг, логаут.

## API Endpoints Used

Все — уже отгружены историями 01 и 04, контракты в `ProductSpecification/api-specs/`.

| Метод | Путь | Статус | Роль в истории |
|---|---|---|---|
| POST | `/api/v1/auth/challenge/start` | ALREADY IMPLEMENTED | тело `{email, challengeType: "EMAIL_CODE"}` → `{challengeId, challengeType, expiresAt}`; 400 / 409 `CONFLICT` + `payload.retryAfterSeconds` / 503 |
| POST | `/api/v1/auth/challenge/verify` | ALREADY IMPLEMENTED | тело `{challengeId, code}` → `{user{id}, session{id, refreshToken, accessToken}}`; 400 / 401 / 503 |
| POST | `/api/v1/auth/token/refresh` | NOT USED (история 05, RED) | — |
| GET | `/api/v1/profile` | NOT USED (заглушка после входа профиль не запрашивает) | — |

Конверт ошибки — общий `{code, message, payload}`. Значения по умолчанию на бэкенде:
TTL challenge 300 с, 5 попыток, кулдаун повторной отправки 60 с
(`AUTH_CHALLENGE_TTL_SECONDS`, `AUTH_CHALLENGE_MAX_ATTEMPTS`,
`AUTH_CHALLENGE_RESEND_COOLDOWN_SECONDS` в `application.yml`). **Фронт эти числа не
знает** — он берёт `expiresAt` и `retryAfterSeconds` из ответов.

## Token / Auth Requirements

- После `verify` фронт держит `accessToken` и `refreshToken` **только в памяти**
  (состояние приложения). Ни `localStorage`, ни Telegram CloudStorage, ни cookie.
- В этой истории токены никуда не отправляются: ни один защищённый эндпоинт не
  вызывается. Нужен лишь факт «сессия есть» для перехода на экран после входа.
- Токены и `session.id` на экране не показываются (`ui-conventions.md`: «Success
  states avoid exposing session or token details»).

## Key Architectural Decisions

DECISION: **Клиент — Telegram Mini App, но без Telegram SDK.** Обычная веб-страница.
Никаких проверок `window.Telegram`, никаких `initData`. SDK появится вместе с историей
06, когда понадобится Telegram-вход.

DECISION: **Сессия в памяти, «пока никуда не сохраняем».** Повторное открытие — новый
вход. Хранение — отдельная история.

DECISION: **Один поток без различия регистрации и входа.** Ни признака «новый
пользователь» в ответе `verify`, ни проверки профиля. Заголовок и тексты экрана
нейтральны: «Войти или создать аккаунт» — не две кнопки, а одна формулировка.

DECISION: **Тексты ошибок — свои на фронте, по `code` и HTTP-статусу.** Поле `message`
из ответа API на экран не выводится; фронт не зависит от формулировок бэкенда.

DECISION: **Причину `401` на `verify` фронт не различает.** Бэкенд намеренно не
разглашает, почему код отклонён (неверный / истёк / попытки исчерпаны — всё `401
UNAUTHORIZED`, различие только в `message`, которое мы не используем). Любой `401` —
одно безопасное сообщение вроде «Код не подошёл. Проверьте письмо или запросите новый»,
поле остаётся открытым, кнопка «Отправить новый код» доступна с учётом кулдауна.

DECISION: **Терминальное состояние на экране кода — только по локальному таймеру.**
Когда обратный отсчёт до `expiresAt` дошёл до нуля, поле кода блокируется, активна
только «Отправить новый код». Это единственный случай, когда фронт сам решает, что
challenge мёртв; всё остальное — ответы API.

DECISION: **Повторная отправка — тот же `challenge/start` с тем же email.** Отдельного
resend-эндпоинта нет (история 01, «Два эндпоинта, больше ни одного»). Новый ответ
приносит новый `challengeId` и `expiresAt`; прежний код обесценен. Кнопка ведёт
собственный обратный отсчёт кулдауна; если бэкенд всё-таки ответил `409`, отсчёт
перезапускается от `payload.retryAfterSeconds`.

## Business Rules & Constraints

- Email валидируется на фронте до отправки минимально (непустой, похож на адрес);
  строгая проверка — на бэкенде, `400` показывается как «Проверьте адрес».
- Код — ровно 6 цифр; кнопка «Подтвердить» неактивна, пока их не шесть. Ведущий ноль
  значим — код передаётся строкой, не числом.
- На экране кода виден адрес, на который ушло письмо, и ссылка «Изменить адрес» —
  возврат на экран email с предзаполненным значением.
- Состояние ожидания при каждом запросе: кнопки блокируются, повторное нажатие не
  создаёт второй запрос.
- `503` на любом шаге — одно сообщение «Сервис временно недоступен, попробуйте позже»
  и возможность повторить действие; без диагностики провайдера.
- Потеря `challengeId` (перезагрузка страницы) — принятое ограничение истории 01:
  пользователь начинает с экрана email и ждёт кулдаун. Ничего не делаем.

## Testing Considerations

DECISION: **Selenium E2E идёт против стаба API, бэкенд не поднимаем.** Код из письма
берётся не из MailHog: стаб на стороне E2E сам знает, какой код «отправил». Реальный
контракт проверяет acceptance-сьют бэкенда; E2E проверяет поведение экрана.

DECISION: **Тесты ждут реальные интервалы и выполняются параллельно.** Кулдаун и
таймер в E2E не укорачиваем через env бэкенда (его и нет) — тест, которому нужен
кулдаун, честно ждёт, а остальные идут параллельно. Обоснование пользователя: «тестов
станет много со временем, и они всё равно не будут успевать за 5 минут» — параллель
нужна в любом случае, а укорачивание ничего не экономит.

ACTION: включить параллельное выполнение в `frontend/e2e` (JUnit Platform
`junit.jupiter.execution.parallel.*`), по одному WebDriver на тест.

ACTION: стаб API. Живёт в `frontend/e2e/` (например, WireMock или лёгкий
HTTP-сервер на JDK), поднимается тестовым запуском на порту из
`frontend/infrastructure/.env`; фронт для E2E запускается с `VITE_API_URL`, указывающим
на стаб. Стаб должен быть безопасен для параллели: состояние — на email (каждый тест
берёт уникальный адрес), код детерминирован для этого адреса, `expiresAt` и
`retryAfterSeconds` отдаёт как реальный бэкенд (300 с / 60 с), чтобы таймер и кулдаун
на экране вели себя как в проде.

ACTION: юнит-лейн (Vitest + MSW) — таймер и кулдаун проверяются с подменой времени
(`vi.useFakeTimers`), там реальных ожиданий нет.

- В E2E-тестах нет Telegram: приложение открывается в обычном Chrome.

Открытый момент (уточнить на ревью интервью): раз стаб сам отдаёт `expiresAt` и
`retryAfterSeconds`, отдельные E2E-тесты на «таймер дошёл до нуля» могут получить от
стаба короткие значения без укорачивания чего-либо на бэкенде и без потери
реалистичности фронта — это альтернатива честному ожиданию, если параллели окажется
мало.
