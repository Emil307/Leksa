# EmailCodeSignupLogin — UI-тесты

> **Implementation Order**: Tests are numbered for sequential TDD implementation.
> Start с отрисовки экрана почты и локальной проверки адреса, затем запрос кода и его
> ошибки, затем ввод и проверка кода, затем истечение и повторная отправка и,
> последними, навигация между экранами и перезагрузка.

**Граница истории.** Приложение проверяется в обычном Chrome без Telegram: SDK не
подключается, поведение внутри Telegram и в браузере одно. Бэкенд не поднимается — все
ответы отдаёт стаб API, живущий рядом с E2E; реальный контракт двух эндпоинтов уже
закрыт acceptance-сьютом бэкенда (история 01) и здесь не переутверждается. Хранение
сессии между открытиями, обновление по refresh-токену и продуктовый экран после входа —
отдельные истории; после входа проверяется только заглушка «вошёл».

Каждый сценарий берёт уникальный адрес: состояние стаба ведётся по адресу, и сценарии
идут параллельно. Сроки и паузы в сценариях — те, что назвал стаб; тест ждёт их
честно, а не подменяет часы приложения.

## 1. Экран почты

### 1.1 Пользователь открывает приложение, получает код на почту и оказывается внутри

Tier: 1 (hz-01, hz-07, hz-08)

```gherkin
Дано пользователь открывает приложение
Тогда виден экран почты с нейтральным заголовком «Войти или создать аккаунт»
И поле адреса пустое и в фокусе
И кнопка «Получить код» недоступна
И ячеек кода, отсчёта и кнопки «Отправить новый код» на экране нет
Когда он вводит свой адрес и нажимает «Получить код»
Тогда сервису ушёл ровно один запрос кода на этот адрес
И виден экран кода с этим адресом
И идёт обратный отсчёт от срока, который назвал сервис
И шесть ячеек кода пусты и первая в фокусе
И кнопка «Подтвердить» недоступна
И кнопка «Отправить новый код» и ссылка «Изменить адрес» доступны
Когда он вводит код, который сервис отправил на его адрес, и нажимает «Подтвердить»
Тогда сервису ушёл ровно один запрос проверки с выданным ему идентификатором и кодом как строкой
И виден экран «вошёл»
И на экране нет ни токенов, ни идентификатора сессии, ни идентификатора запроса кода
```

## 2. Запрос кода

### 2.1 Отсчёт начинается с того же значения при часах браузера в другом поясе

Tier: 2 (hz-01)

```gherkin
Дано пользователь на экране почты ввёл свой адрес, а часы браузера в другом поясе
Когда он нажимает «Получить код»
Тогда идёт обратный отсчёт от срока, который назвал сервис, — с того же значения, что и при часах в поясе сервиса
```

### 2.2 Пока идёт запрос кода, кнопка недоступна и повторное нажатие второго запроса не создаёт

Tier: 2 (hz-02, hz-03, hz-04, hz-08)

```gherkin
Дано пользователь на экране почты ввёл свой адрес
И сервис отвечает на запрос кода с задержкой
Когда он нажимает «Получить код» дважды подряд и ещё раз нажимает Enter в поле адреса
Тогда кнопка недоступна, пока ответ не пришёл
И сервису ушёл ровно один запрос кода
И после ответа виден экран кода
```

### 2.4 Пауза между отправками ещё не прошла — кнопка закрыта на время, которое назвал сервис

Tier: 2 (hz-01, hz-02, hz-04, hz-07, hz-08)

```gherkin
Дано для адреса пользователя код уже запрашивали, и пауза между отправками ещё идёт
И пользователь на экране почты ввёл этот адрес
Когда он нажимает «Получить код»
Тогда он остаётся на экране почты
И видно сообщение «Новый код можно запросить через N с», где N — пауза, которую назвал сервис
И кнопка «Получить код» недоступна, а сообщение отсчитывает секунды
Когда пауза, которую назвал сервис, проходит
Тогда кнопка «Получить код» снова доступна и сообщение исчезает
```

### 2.5 Сервис недоступен при запросе кода — одно сообщение и возможность повторить

Tier: 2 (hz-02, hz-05, hz-06, hz-07, hz-08)

```gherkin
Дано пользователь на экране почты ввёл свой адрес
И сервис временно недоступен
Когда он нажимает «Получить код»
Тогда он остаётся на экране почты
И видно сообщение «Сервис временно недоступен, попробуйте позже» без подробностей
И кнопка «Получить код» снова доступна
И сервису ушёл ровно один запрос кода — приложение не повторяет его само
Когда сервис снова доступен и он нажимает «Получить код»
Тогда виден экран кода с его адресом
```

## 3. Ввод и проверка кода

### 3.2 Код с ведущим нулём уходит как строка, ноль на месте

Tier: 2 (hz-01)

```gherkin
Дано пользователь на экране кода, а код, который сервис отправил на его адрес, начинается с нуля
Когда он вводит этот код и нажимает «Подтвердить»
Тогда запрос проверки несёт код как строку из шести символов, ведущий ноль на месте
И виден экран «вошёл»
```

### 3.3 Пока идёт проверка кода, кнопка недоступна и второго запроса нет

Tier: 2 (hz-02, hz-03, hz-04, hz-08)

```gherkin
Дано пользователь на экране кода ввёл код, который сервис отправил на его адрес
И сервис отвечает на проверку с задержкой
Когда он нажимает «Подтвердить» дважды подряд
Тогда кнопка недоступна и ячейки закрыты, пока ответ не пришёл
И сервису ушёл ровно один запрос проверки
И после ответа виден экран «вошёл»
```

### 3.4 Отклонённый код показывается одним сообщением, поле открыто для новой попытки

Tier: 2 (hz-02, hz-04, hz-07, hz-08)

```gherkin
Дано пользователь на экране кода
И сервис отклоняет проверку с формулировкой <причина от сервиса>
Когда он вводит шесть цифр и нажимает «Подтвердить»
Тогда видно сообщение «Код не подошёл. Проверьте письмо или запросите новый»
И формулировка сервиса на экране не появляется
И ячейки кода пусты и открыты, отсчёт продолжается
И кнопка «Отправить новый код» доступна
Когда он вводит код, который сервис отправил на его адрес, и нажимает «Подтвердить»
Тогда виден экран «вошёл»
```

| причина от сервиса |
|---|
| неверный код |
| код истёк |
| попытки исчерпаны |

## 4. Истечение кода и повторная отправка

### 4.1 Отсчёт дошёл до нуля — поле кода закрыто, доступна только повторная отправка

Tier: 2 (hz-01, hz-04, hz-07, hz-08)

```gherkin
Дано пользователь на экране кода, срок кода для его адреса — несколько секунд
Когда отсчёт доходит до нуля
Тогда отсчёт показывает «0:00» и видно сообщение «Срок кода истёк — запросите новый»
И ячейки кода закрыты для ввода и кнопка «Подтвердить» недоступна
И кнопка «Отправить новый код» и ссылка «Изменить адрес» доступны
И запрос проверки не отправляется
```

### 4.2 «Отправить новый код» приносит новый код, прежний перестаёт действовать, отсчёт начинается заново

Tier: 2 (hz-02, hz-03, hz-04, hz-06, hz-07, hz-08)

```gherkin
Дано пользователь на экране кода ввёл три цифры, срок первого кода для его адреса короткий, а пауза между отправками прошла
Когда он нажимает «Отправить новый код»
Тогда сервису ушёл ровно один новый запрос кода на тот же адрес
И ячейки кода пусты и открыты, отсчёт начался заново от срока, который назвал сервис
Когда срок первого кода проходит
Тогда ячейки остаются открытыми, сообщения об истечении нет, отсчёт идёт от нового срока
Когда он вводит прежний код и нажимает «Подтвердить»
Тогда видно сообщение «Код не подошёл. Проверьте письмо или запросите новый»
Когда он вводит новый код, который сервис отправил на его адрес, и нажимает «Подтвердить»
Тогда запрос проверки несёт новый идентификатор запроса кода
И виден экран «вошёл»
```

### 4.3 Повтор внутри паузы — письмо не уходит, кнопка закрывается на время, которое назвал сервис

Tier: 2 (hz-01, hz-02, hz-03, hz-04, hz-07, hz-08)

```gherkin
Дано пользователь на экране кода <в состоянии>, пауза между отправками для его адреса ещё идёт
Когда он нажимает «Отправить новый код»
Тогда кнопка «Отправить новый код» недоступна и показывает «Новый код можно запросить через N с», где N — пауза, которую назвал сервис
И состояние ячеек и отсчёта не меняется, запрос проверки не отправляется
Когда пауза, которую назвал сервис, проходит
Тогда кнопка «Отправить новый код» снова доступна
Когда он вводит код, который сервис отправил на его адрес, и нажимает «Подтвердить»
Тогда запрос проверки несёт прежний идентификатор запроса кода
И виден экран «вошёл»
```

| в состоянии |
|---|
| отсчёт идёт, ячейки открыты |
| срок истёк, ячейки закрыты — после паузы повторная отправка открывает их заново |

## DSL Technical Reference

| DSL Statement | Technical Implementation |
|---|---|
| `пользователь открывает приложение` | Chrome (Selenium) открывает `http://FRONTEND_HOST:FRONTEND_PORT/` из `frontend/infrastructure/.env`; `VITE_API_URL` указывает на стаб |
| `сервис` / `стаб` | HTTP-стаб в `frontend/e2e/`, состояние по email; реальный бэкенд не поднимается |
| `свой адрес` | уникальный email на сценарий, например `ui-{scenario}-{random}@example.test` |
| `запрос кода` | POST /api/v1/auth/challenge/start `{email, challengeType: "EMAIL_CODE"}`; стаб отвечает `{challengeId, challengeType, expiresAt}` |
| `срок, который назвал сервис` | `expiresAt` из ответа `start`; по умолчанию 300 с, для сценария 4.1 стаб отдаёт короткий срок этому адресу |
| `пауза между отправками ещё идёт` | стаб уже выдал challenge этому адресу меньше 60 с назад и на новый `start` отвечает 409 `{code: "CONFLICT", payload: {retryAfterSeconds}}` |
| `пауза … прошла` | тест ждёт `retryAfterSeconds` (по умолчанию 60 с) реальным временем; сценарии идут параллельно |
| `адрес, который сервис не принимает` | стаб на `start` отвечает 400 `{code: "VALIDATION_FAILED"}` |
| `сервис временно недоступен` / `снова доступен` | стаб отвечает 503 `{code: "UNAVAILABLE"}` до переключения тестом |
| `отвечает с задержкой` | стаб задерживает ответ на несколько секунд для этого адреса |
| `код, который сервис отправил на его адрес` | детерминированный код стаба для этого адреса и текущего `challengeId` |
| `запрос проверки` | POST /api/v1/auth/challenge/verify `{challengeId, code}`; `code` — строка |
| `сервис отклоняет проверку с формулировкой` | стаб отвечает 401 `{code: "UNAUTHORIZED", message}` с указанным `message` |
| `экран «вошёл»` | заглушка после входа; ответ `verify` `{user{id}, session{id, accessToken, refreshToken}}` держится только в памяти |
| `ровно один запрос` | стаб ведёт журнал запросов по адресу; тест читает его через служебный эндпоинт стаба |
| `перезагружает страницу` | `driver.navigate().refresh()` |
| `«Назад» / «Вперёд» в браузере` | `driver.navigate().back()` / `forward()` |
| `часы браузера в другом поясе` | CDP `Emulation.setTimezoneOverride` (например `Asia/Tokyo`); `expiresAt` стаба — ISO-8601 с зоной |
| `ответ, которого приложение не ждёт` | стаб для этого адреса отдаёт указанный статус/тело; тест читает `driver.manage().logs().get(BROWSER)` на уровень SEVERE |
| `срок первого кода короткий` | стаб отдаёт первому `start` этого адреса `expiresAt` через несколько секунд, второму — 300 с |
| `с задержкой дольше остатка срока` | стаб задерживает ответ `verify` на несколько секунд; «код принят» — 200, «код отклонён» — 401 |
| `срок кода уже в прошлом` / `пауза … равна нулю` | стаб отдаёт `expiresAt` в прошлом / 409 с `retryAfterSeconds: 0` |
| `адрес на проводе байт в байт` | тело `start` в журнале стаба сравнивается со строкой как UTF-8 |
| `не повторяет его само` | журнал стаба для адреса содержит один запрос через несколько секунд после отказа |
