# EmailCodeLogin — тесты безопасности

> **Implementation Order**: Tests are numbered for sequential TDD implementation.
> Start с границ ввода на обеих ручках, затем подмена серверных полей, затем область
> действия идентификатора challenge и, последними, утверждения о нераскрытии секретов.

**Граница истории.** Три блока вынесены в отдельные истории:

- **Отрисовка шаблона письма и отправка по SMTP** — поэтому здесь нет утверждений об
  экранировании в теле письма и о заголовках конверта. Утверждается то, что принадлежит
  `start`: враждебное значение доходит до заявки как есть, не рвёт лог и не пересекается
  по ключу хранилища.
- **Проверка access-токена** (бывшая секция 4: подпись, алгоритм, срок, состав полезной
  нагрузки) — в этой истории нет ни одного эндпоинта, принимающего токен, поэтому
  предъявить его некуда. Блок переезжает в историю первого защищённого эндпоинта. Номер
  4 не переиспользуется.
- **Тела ошибок при отказе хранилищ** — строки «временно недоступен» ушли из таблицы 5.2
  вместе с историей про устойчивость.

**Отфильтровано как неприменимое к поверхности этой истории** (не пишем сценарии):
CSRF — авторизация bearer-токеном, куки не используются; хеширование паролей — вход
passwordless, пароля нет вообще; XSS — пользовательский текст никуда не отрисовывается;
инъекции NoSQL/LDAP/XXE — таких технологий в стеке нет; SSRF — ни одна ручка не ходит по
адресу из запроса; фиксация сессии — каждая успешная проверка создаёт новую строку
сессии, а подстановка `session.id` клиентом закрыта сценарием 2.1; общие 401 для
неаутентифицированного, заголовки безопасности, CORS и HTTPS — сквозные, проверяются
глобально, а не в истории.

## 1. Границы ввода

### 1.1 Ввод сверх объявленных границ отклоняется до постановки заявки

Tier: 2 (sec:InputLength, hz-01, hz-06, hz-08)

```gherkin
Дано в системе нет живого challenge и нет заявок в очереди
Когда клиент отправляет <ввод>
Тогда запрос отклоняется как некорректные данные
И заявка в очередь не кладётся
И живой challenge не создаётся
```

| ввод |
|---|
| email на запросе кода длиной 255 октетов при лимите 254 |
| email на запросе кода — многобайтовый адрес, укладывающийся в 254 символа, но не в 254 октета |
| код на проверке из 7 цифр |
| тело запроса кода на несколько мегабайт |
| тело запроса проверки на несколько мегабайт |

### 1.3 Инъекция в поля запроса не доходит до базы и не ломает запрос

Tier: 2 (sec:SQLi, sec:InputValidation, hz-05)

```gherkin
Дано в системе есть зарегистрированный пользователь
Когда клиент отправляет <поле> со значением, составленным как фрагмент SQL
Тогда запрос отклоняется как некорректные данные либо обрабатывается как обычное значение
И ни одна таблица не изменена сверх штатного поведения запроса
И тело ответа не несёт ни текста SQL, ни имени ограничения базы данных
```

| поле |
|---|
| email на запросе кода |
| идентификатор challenge на проверке |
| код на проверке |

---

### 1.4 Враждебный email не рвёт лог и не пересекается с чужим ключом

Tier: 2 (sec:InputValidation, hz-01, hz-05, hz-07)

```gherkin
Дано адрес содержит <враждебная часть>
Когда клиент запрашивает код на этот адрес
Тогда либо запрос отклоняется как некорректные данные, либо адрес попадает в заявку ровно тем значением, которое пришло
И строка лога не разрывается на две
И ключ хранилища этого адреса не совпадает с ключом другого адреса
И маска адреса в логе остаётся корректным текстом — без символа замены и без разорванной последовательности
```

| враждебная часть |
|---|
| последовательность возврата каретки и перевода строки |
| многобайтовые символы на границе маскирования в логе |

## 2. Подмена серверных полей

### 2.1 Серверные поля, присланные клиентом, игнорируются

Tier: 2 (sec:MassAssignment, hz-04, hz-05, hz-08)

```gherkin
Дано в системе нет живого challenge
Когда клиент отправляет запрос, в теле которого дополнительно прислано поле <поле>
Тогда запрос обрабатывается штатно
И побеждает значение, сгенерированное сервером
И присланное значение не попало ни в ответ, ни в хранилище
```

| поле | ручка |
|---|---|
| `challengeId`, `expiresAt`, `status` | запрос кода |
| `code` | запрос кода |
| `uniquenessKey` | запрос кода |
| `retryAfterSeconds` | запрос кода |
| `email` | проверка кода — личность берётся из сохранённого challenge, а не из тела |
| `provider`, `providerId` | проверка кода |
| `userId`, `name` | проверка кода |
| `sessionId`, `refreshToken`, `accessToken` | проверка кода |
| `attempts`, `attemptsRemaining` | проверка кода |

### 2.2 Тип challenge без зарегистрированной стратегии отклоняется явно

Tier: 2 (sec:InputValidation, hz-04, hz-05)

```gherkin
Дано в перечислении типов challenge есть значение, для которого стратегия не зарегистрирована
Когда клиент запрашивает код с этим типом
Тогда запрос отклоняется явной ошибкой
И ветка по умолчанию не выбирается
И заявка в очередь не кладётся
```

## 3. Область действия идентификатора challenge

### 3.1 Чужой идентификатор challenge не даёт ни сессии, ни сведений о существовании

Tier: 2 (sec:IDOR, hz-05, hz-08)

```gherkin
Дано два разных пользователя получили каждый свой код
Когда первый пользователь предъявляет идентификатор challenge второго со своим кодом
Тогда проверка отклоняется как неудачная авторизация
И сессия второму пользователю не выдаётся
И ответ не отличается от ответа на неверный код по собственному живому challenge — по нему нельзя отличить чужой живой challenge от своего
И попытки у challenge первого пользователя не тратятся
И верный код второго пользователя по-прежнему выдаёт сессию
```

Объявленное ограничение, а не пробел: `verify` не аутентифицирован — код и есть
удостоверение, а идентификатор challenge отдаётся только запросившему. Кто им уже
владеет, неотличим от инициатора, поэтому он может израсходовать попытки — выход из
этого состояния описан сценарием 3.2 и API-сценарием 2.5.

## DSL Technical Reference

| DSL Statement | Technical Implementation |
|---------------|-------------------------|
| `клиент запрашивает код` | POST /api/v1/auth/challenge/start |
| `клиент отправляет на проверку` | POST /api/v1/auth/challenge/verify |
| `запрос отклоняется как некорректные данные` | 400 `{code: "VALIDATION_FAILED"}` |
| `проверка отклоняется как неудачная авторизация` | 401 `{code: "UNAUTHORIZED"}` |
| `запрос отклоняется по кулдауну` | 409 `{code: "CONFLICT", payload:{retryAfterSeconds}}` |
| `дополнительно присланное поле` | лишнее свойство тела запроса (обе схемы — `additionalProperties: true`) |
| `заявка в очереди` | строка `notifications.t_outbox` |
| `переменные шаблона заявки` | `notifications.t_outbox.data.variables` |
| `лимит попыток` | `CHALLENGE_MAX_ATTEMPTS` |
| `кулдаун` | `CHALLENGE_RESEND_COOLDOWN_SECONDS` |
| `ключ хранилища адреса` | `challenge:key:{challengeType}:{uniquenessKey}` в Redis |
| `узнаваемая метка` | сентинельное значение, засеянное тестом и искомое по всем поверхностям вывода |
| `объявленная форма маски` | зафиксированный вид маскированного email в логе |
| `идентификатор корреляции` | поле корреляции в конверте ошибки и в строке лога |
| `бюджет времени ответа` | измерение wall-clock вокруг HTTP-запроса |
