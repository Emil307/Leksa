# EmailCodeLogin — API-тесты

> **Implementation Order**: Tests are numbered for sequential TDD implementation.
> Start с отказов валидации на запросе кода, затем счастливый путь запроса кода,
> затем валидация и счастливый путь проверки кода, затем терминальные состояния
> challenge, повтор проверки, одновременные запросы и, последними, сквозные
> утверждения о времени, нормализации и конфигурации.

**Граница истории.** `start` кладёт заявку в очередь писем и на этом заканчивается.
Планировщик, разбирающий очередь, отправка письма по SMTP и чистка очереди — отдельные
истории. Поэтому здесь ни один сценарий не читает почтовый ящик: наблюдаемый выход
`start` — строка очереди, и код для проверки берётся из неё.

**Отказы хранилищ тоже вынесены** в отдельную историю: недоступный, зависший и перезапущенный Redis, отказ транзакции базы данных, откат при отказе очереди, нечитаемая запись challenge, значения конфигурации по умолчанию. Эта история считает Redis и PostgreSQL доступными. Ушедшие номера — 2.8, 2.9, 5.7, 6.3, 6.4, 8.3 — не переиспользуются. Все сценарии с пометкой «через управляемую точку синхронизации» задают гонку детерминированно: два вызова доводятся до фиксированной точки внутри окна чтения-записи и отпускаются вместе. «Отправлены одновременно» без такой точки — недостаточная формулировка: гарантия, срабатывающая в 99 % прогонов, не гарантия.

## 1. Валидация запроса кода

### 1.1 Некорректное тело запроса кода отклоняется до постановки заявки в очередь

```gherkin
Дано в системе нет живого challenge и нет заявок в очереди
Когда клиент запрашивает код, в теле которого <поле> имеет значение <значение>
Тогда запрос отклоняется как некорректные данные
И заявка в очередь не кладётся
И живой challenge не создаётся
```

| поле          | значение                                                                 |
| ------------- | ------------------------------------------------------------------------ |
| email         | отсутствует в теле                                                       |
| email         | null                                                                     |
| email         | пустая строка                                                            |
| email         | адрес без символа «собака»                                               |
| email         | адрес без доменной части                                                 |
| тип challenge | отсутствует в теле — единственное значение перечисления не подставляется |
| тип challenge | null                                                                     |
| тип challenge | пустая строка                                                            |
| тип challenge | неизвестное значение `SMS_CODE`                                          |

## 2. Запрос кода

### 2.1 Запрос кода возвращает challenge и кладёт в очередь готовую заявку

Tier: 1 (hz-07)

```gherkin
Дано в системе нет живого challenge и нет заявок в очереди
Когда клиент запрашивает код на свой email
Тогда ответ несёт идентификатор challenge, его тип и момент истечения
И момент истечения равен моменту создания плюс настроенное время жизни кода
И в очереди лежит ровно одна ожидающая заявка
И заявка несёт адресата, отправителя, тему, путь шаблона, идентификатор письма и код в переменных шаблона
И код в заявке — тот же, который сохранён в challenge
И в ответе нет ни кода, ни адреса перехода, ни состояния challenge
```

**Где что проверяется.** Три утверждения об HTTP-ответе — идентификатор, тип и момент
истечения, а также отсутствие кода, адреса перехода и состояния — проверяются
acceptance-тестом. Четыре утверждения об очереди проверяются на уровнях, откуда очередь
видна: содержимое заявки и совпадение кода — тестом юзкейса, единственность строки и её
запись — тестом storage-адаптера. Acceptance-сьюта ходит только по HTTP и в базу не
заглядывает, а эндпоинта «покажи очередь» нет и он не является целью.

**Совпадение кода читается как инвариант, а не как сквозной проход.** Утверждение
требует, чтобы в заявку уехал тот же самый код, который сохранён в challenge, — не
чтобы этот код был скормлен `verify`. Проверка кода принадлежит сценарию 4.1 и здесь не
строится; полный путь «код из заявки → сессия» описан сценарием 2.3 в `tier3/`.

### 2.4 Повторный запрос внутри кулдауна отклоняется и второй заявки не создаёт

Tier: 2 (hz-02, hz-08)

```gherkin
Дано пользователь только что запросил код на свой email
Когда клиент запрашивает код на тот же email, не дожидаясь конца кулдауна
Тогда запрос отклоняется по кулдауну
И ответ несёт остаток ожидания целыми секундами
И вторая заявка в очередь не кладётся
И ранее выданный код по-прежнему выдаёт сессию
И клиент, потерявший идентификатор challenge, до конца кулдауна войти не может — это объявленное ограничение, а выход из него описан сценарием 2.5
```

### 2.5 Повторный запрос после кулдауна выдаёт новый challenge и обесценивает прежний код

Tier: 2 (hz-02, hz-08)


## 7. Одновременные запросы

### 7.1 Два одновременных запроса кода дают одну заявку и один живой challenge

Tier: 2 (hz-02, hz-03, hz-08)

```gherkin
Дано в системе нет живого challenge для этого email
Когда два запроса кода на один email доведены до управляемой точки синхронизации внутри захвата кулдауна и отпущены вместе
Тогда ровно один из них создаёт challenge
И проигравший получает отказ по кулдауну, потому что захват кулдауна условный, а не «прочитал и записал»
И в очередь попадает ровно одна заявка
```

```gherkin
Тогда оба ответа успешны и несут один и тот же идентификатор сессии
```

## 8. Время, нормализация и конфигурация

### 8.1 Время жизни проходит от конфигурации до сроков токенов без искажений

Tier: 2 (hz-01, hz-07)

```gherkin
Дано часы системы зафиксированы на моменте, который не приходится на целую секунду
И время жизни кода и сроки токенов заданы конфигурацией так, что их сумма с этим моментом тоже не целая
Когда пользователь запрашивает код и входит по нему
Тогда момент истечения из ответа равен моменту запроса плюс настроенное время жизни кода, вплоть до долей секунды
И проверка непосредственно до момента истечения успешна
И проверка сразу после момента истечения отклоняется
И срок access-токена равен моменту выдачи плюс настроенный срок access-токена
И срок созданной строки сессии равен моменту выдачи плюс настроенный срок refresh-токена
```

### 8.2 Остаток кулдауна отдаётся целыми секундами на всех границах

Tier: 2 (hz-01, hz-04, hz-07)

```gherkin
Дано часы системы зафиксированы
И пользователь только что запросил код
Когда клиент запрашивает код повторно в момент <момент>
Тогда результат — <результат>
```

| момент                                 | результат                                                                                                              |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| за 2,5 секунды до конца кулдауна       | отказ по кулдауну с остатком ровно 3 (округление вверх — иначе клиент, честно выждавший остаток, снова получает отказ) |
| за 0,1 секунды до конца кулдауна       | отказ по кулдауну с остатком ровно 1, никогда 0                                                                        |
| ровно в конце кулдауна                 | запрос принимается                                                                                                     |
| через 0,1 секунды после конца кулдауна | запрос принимается                                                                                                     |

### 8.4 Регистр и форма записи email — одна личность

Tier: 2 (hz-01, hz-03, hz-07)


## DSL Technical Reference

| DSL Statement                                    | Technical Implementation                                                                                                               |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| `клиент запрашивает код на <email>`              | POST /api/v1/auth/challenge/start `{email, challengeType: "EMAIL_CODE"}`                                                               |
| `клиент отправляет на проверку …`                | POST /api/v1/auth/challenge/verify `{challengeId, code}`                                                                               |
| `выдаётся сессия`                                | 200 + `{user:{id}, session:{id, refreshToken, accessToken}}`                                                                           |
| `запрос отклоняется как некорректные данные`     | 400 `{code: "VALIDATION_FAILED"}`                                                                                                      |
| `проверка отклоняется как неудачная авторизация` | 401 `{code: "UNAUTHORIZED"}`                                                                                                           |
| `запрос отклоняется по кулдауну`                 | 409 `{code: "CONFLICT", payload:{retryAfterSeconds}}`                                                                                  |
| `заявка в очереди`                               | строка `notifications.t_outbox` (`type`, `status`, `data`, `attempts`, `last_error`)                                                   |
| `ожидающая заявка`                               | `notifications.t_outbox.status = ACTIVE`                                                                                               |
| `код из заявки`                                  | `notifications.t_outbox.data.variables.code` — единственный наблюдаемый выход `start`, пока доставка не реализована отдельной историей |
| `переменные шаблона`                             | `notifications.t_outbox.data.variables`                                                                                                |
| `управляемая точка синхронизации`                | барьер/защёлка в тестовом двойнике порта, освобождающая оба вызова в одной точке кода                                                  |
| `живой challenge`                                | ключ `challenge:{challengeId}` в Redis с ненулевым TTL                                                                                 |
| `кулдаун взведён`                                | ключ `challenge:cooldown:{challengeType}:{uniquenessKey}` в Redis                                                                      |
| `захват кулдауна условный`                       | атомарная установка-если-нет-со-сроком; проигравший получает «не установлено»                                                          |
| `запись о повторе`                               | ключ `challenge:verified:{challengeId}` в Redis                                                                                        |
| `учётная запись провайдера «email»`              | строка `auth.t_auth` с `(provider='email', provider_id=нормализованный email)`                                                         |
