# EmailCodeLogin

## Brief Description

Вход по email без пароля. Клиент запрашивает код, пользователь получает 6 цифр письмом, отправляет их обратно и получает сессию.

## Configuration

Все числа ниже — настройки, а не константы в коде. Тесты берут значения отсюда, а не пишут цифры руками.

| Настройка                           | Что задаёт                                     | Значение по умолчанию |
| ----------------------------------- | ---------------------------------------------- | --------------------- |
| `CHALLENGE_TTL_SECONDS`             | сколько живёт код                              | 300                   |
| `CHALLENGE_MAX_ATTEMPTS`            | сколько неверных кодов убивают challenge       | 5                     |
| `CHALLENGE_RESEND_COOLDOWN_SECONDS` | пауза между двумя `start` для одного email     | 60                    |
| `CHALLENGE_REPLAY_WINDOW_SECONDS`   | сколько повторный `verify` отдаёт ту же сессию | 60                    |
| `ACCESS_TOKEN_TTL_SECONDS`          | срок жизни access-JWT                          | 1800                  |
| `REFRESH_TOKEN_TTL_SECONDS`         | срок жизни refresh-токена                      | 31536000 (1 год)      |
| `OUTBOX_POLL_INTERVAL_SECONDS`      | как часто воркер заглядывает в очередь         | 2                     |
| `OUTBOX_BATCH_SIZE`                 | сколько строк воркер берёт за один заход       | 10                    |
| `OUTBOX_MAX_ATTEMPTS`               | сколько раз пытаемся отправить одно письмо     | 5                     |
| `OUTBOX_PROCESS_TIMEOUT_SECONDS`    | когда зависший `PROCESS` возвращается в очередь | 60                   |
| `OUTBOX_RETENTION_HOURS`            | сколько живут терминальные строки до чистки    | 24                    |
| `MAIL_TIMEOUT_SECONDS`              | таймаут подключения и чтения SMTP              | 5                     |
| `MAIL_TEMPLATE_NAMESPACE`           | UUID в пути шаблона письма                     | из конфигурации       |

## Flow

1. Клиент шлёт `email` + `challengeType=EMAIL_CODE` на `POST /api/v1/auth/challenge/start`.
2. Запрос валидируется: сначала длина email, потом формат.
3. По `challengeType` выбирается стратегия. Она же говорит, чем challenge уникален: для `EMAIL_CODE` это
   нормализованный email.
4. Под этим ключом атомарно ставится кулдаун `CHALLENGE_RESEND_COOLDOWN_SECONDS`. Не получилось поставить — значит кулдаун уже стоит, и запрос отклоняется.
5. Сервис генерирует 6-значный код и одной атомарной операцией Redis сохраняет новый challenge и удаляет предыдущий для того же ключа.
6. Сервис вставляет в `notifications.t_outbox` строку со статусом `ACTIVE` — это заявка на письмо, а не само письмо.
   Порядок важен: строка пишется **после** того, как challenge сохранён в Redis, иначе письмо с кодом может уйти
   раньше, чем появится challenge, который этот код проверяет. Если вставка не удалась, новый challenge и кулдаун
   снимаются, `start` отвечает ошибкой.
7. `start` возвращает `challengeId`, `challengeType`, `expiresAt`. Письма в этот момент ещё нет — оно уйдёт, когда до
   строки доберётся воркер.
8. Клиент шлёт `challengeId` + `code` на `POST /api/v1/auth/challenge/verify`.
9. Redis одной атомарной операцией сравнивает код: совпал — удаляет challenge, не совпал — увеличивает счётчик
   неудачных попыток.
10. Если код совпал, одна транзакция БД:

- находит пользователя по email, который лежит в записи challenge (не по email из запроса — его там вообще нет);
  - если пользователя нет — создаёт (`auth.t_users`, `name=''`);
  - создаёт строку `auth.t_auth` для пары `('email', нормализованный email)`, если её ещё нет. Это делается независимо от того, создавали мы пользователя сейчас или он уже был: человек, который раньше заходил через другого провайдера, при первом входе по почте получает свою email-строку;
  - вставляет строку в `auth.t_sessions` со свежим refresh-токеном.

11. Выданные `session.id` и `user.id` записываются под погашенный `challengeId` на время окна повтора.
12. Подписывается access-JWT. Ответ: `user.id` и `session {id, refreshToken, accessToken}`. Повтор того же запроса
    внутри окна повтора вернёт ту же сессию, а не создаст вторую.

## Отправка письма

Письмо уходит не из запроса, а через outbox. Модуль авторизации не знает ни про SMTP, ни про шаблоны, ни про воркер —
он кладёт строку в `notifications.t_outbox` и на этом заканчивает. Модуль уведомлений не знает про challenge — он
разбирает очередь.

**Строка очереди.** Тип лежит в колонке `type`, полезная нагрузка — в `data` (jsonb). Конверта с продублированными
`type`, `eventId` и `timestamp` нет: модуль уведомлений живёт внутри того же приложения, наружу `data` не публикуется,
а идентичность строки — это её `id`.

```json
{
  "to": "user@example.com",
  "from": "no-reply@uwords.local",
  "subject": "Код подтверждения",
  "messageId": "626bee2f-e547-4568-8c15-d21d74d685d2",
  "templatePath": "email/{MAIL_TEMPLATE_NAMESPACE}/email-code",
  "variables": { "code": "111111" }
}
```

**Что делает воркер.** Раз в `OUTBOX_POLL_INTERVAL_SECONDS` берёт до `OUTBOX_BATCH_SIZE` строк запросом
`SELECT ... FOR UPDATE SKIP LOCKED` — бэкенд работает в нескольких экземплярах, и без `SKIP LOCKED` два инстанса
возьмут одну строку и человек получит два письма. Взятая строка переходит в `PROCESS`, отправленная — в `COMPLETED`.

**Когда отправка не удалась.** `attempts` увеличивается, текст ошибки пишется в `last_error`, строка возвращается в
`ACTIVE` и будет взята снова. После `OUTBOX_MAX_ATTEMPTS` попыток строка переходит в `FAILED` и больше не берётся.

**Когда воркер упал посреди отправки.** Строка остаётся в `PROCESS` и никем не подхватывается. Через
`OUTBOX_PROCESS_TIMEOUT_SECONDS` после последнего `updated_at` она возвращается в `ACTIVE`. Отдельная колонка для
этого не нужна — хватает `updated_at`.

**Просроченный код не отправляется.** Строка, созданная раньше чем `CHALLENGE_TTL_SECONDS` назад, уходит в `FAILED`
без попытки отправки: письмо с кодом, который уже не работает, хуже, чем отсутствие письма.

**Код не остаётся в базе.** При переходе в `COMPLETED` или `FAILED` ключ `variables` затирается. Остальное (`to`,
`subject`, `templatePath`, `messageId`) остаётся для разбора инцидентов, а 6-значный код входа живёт в таблице ровно
столько, сколько нужно, чтобы его отправить.

**Чистка.** Регулярная задача в самой БД (`pg_cron`) удаляет `COMPLETED` и `FAILED` старше `OUTBOX_RETENTION_HOURS`.
`ACTIVE` и `PROCESS` не удаляются никогда — иначе чистка съест неотправленное письмо.

**Чем за это заплачено.** `start` больше не может сказать «письмо не ушло»: он отвечает 200, а если SMTP лежит,
человек просто не получает код и не понимает, почему. Взамен письмо доходит само, когда SMTP оживёт, — при условии,
что это случится в пределах жизни кода. Размен принят осознанно, поэтому интервал опроса задан в секундах, а не в
минутах.

## Acceptance Criteria

- Существующий пользователь: получил код, проверил — получил сессию и id своего пользователя.
- Новый email: получил код, проверил — пользователь создан, сессия выдана.
- Второй `start` для того же email убивает предыдущий код: работает только последний.
- Проверенный код не выдаёт вторую сессию. Повтор той же пары `challengeId` + `code` внутри окна повтора возвращает
  тот же `session.id` и тот же `refreshToken`; после окна — отказ.
- Код перестаёт работать, когда истекает `CHALLENGE_TTL_SECONDS`.
- После `CHALLENGE_MAX_ATTEMPTS` неверных кодов challenge удаляется: следующий запрос отклоняется даже с верным кодом.
- Повторный `start` для того же email внутри кулдауна отклоняется, строку в outbox не создаёт и не ломает уже
  отправленный код.
- Два одновременных `verify` с верным кодом дают ровно одну сессию.
- Неизвестный `challengeType` и некорректный email отклоняются до создания строки в outbox.
- SMTP, лежавший в момент `start`, не съедает код: письмо уходит, как только он оживёт, если это случилось в пределах
  жизни кода.

## Required Guards

Собрано из прохода по каталогу опасностей. Каждый пункт — гарантия, которую `/test-spec` обязан превратить в сценарий,
падающий на названной опасности.

**Представление данных и границы**

- Код с ведущим нулём (`012345`) проходит весь путь генерация → письмо → проверка и выдаёт сессию `[hz-01]`.
- Код из не-ASCII цифр (`١٢٣٤٥٦`, `１２３４５６`) отклоняется как `VALIDATION_FAILED` и не тратит попытку. Причина: в Python
  `'١٢٣٤٥٦'.isdigit()` возвращает `True`, `int('١٢٣٤٥٦')` возвращает `123456`, а `\d` в регулярке по умолчанию их
  матчит — то есть наивная проверка их пропустит, и такой код может совпасть с настоящим `[hz-01/hz-05]`.
- Верный код, отправленный последней доступной попыткой (после `CHALLENGE_MAX_ATTEMPTS - 1` неверных), всё ещё выдаёт
  ровно одну сессию `[hz-01]`.
- Email на 255 октетов (лимит 254) и код из 7 цифр отклоняются до отправки письма `[hz-06/hz-05]`.
- Длина email проверяется **до** проверки формата. Иначе специально составленный длинный адрес заставит регулярку
  работать экспоненциально долго (ReDoS). Тест: `start` с патологическим адресом укладывается в заявленный бюджет
  времени ответа `[hz-06]`.
- `User@Example.COM` и `user@example.com` — это один ключ уникальности, один кулдаун и одна строка `auth.t_users`.
  Проверяется под турецкой локалью (где `I` в нижнем регистре даёт `ı`) и на вариантах NFC/NFD `[hz-01/hz-03/hz-05]`.

**Порядок, атомарность и отказы**

- Два одновременных `start` для одного email дают одно письмо и один живой challenge; проигравший получает отказ по
  кулдауну `[hz-03/hz-08]`.
- `CHALLENGE_MAX_ATTEMPTS` одновременных `verify` с неверным кодом полностью съедают лимит: следующий запрос с верным
  кодом получает отказ `[hz-03]`.
- Два одновременных `verify` для одного и того же нового email создают одну строку `auth.t_users`, и проигравший гонку
  получает сессию, а не ошибку нарушения уникальности `[hz-02/hz-03]`.
- Пользователь уже есть в `auth.t_users` (зашёл когда-то через другого провайдера), но строки `auth.t_auth` с
  `provider='email'` у него нет. Первый вход по почте создаёт ровно одну такую строку; второй вход новой не добавляет
  `[hz-02/hz-04]`.
- Если вставка строки в outbox не удалась, после запроса не остаётся ни живого challenge, ни кулдауна, ни убитого
  предыдущего challenge: немедленный повтор `start` принимается и доставляет рабочий код `[hz-02/hz-04]`.
- Строка в outbox появляется только после того, как challenge сохранён в Redis. Обратного порядка не бывает: письма с
  кодом от challenge, которого нет, не существует `[hz-02/hz-03]`.
- Если транзакция БД в `verify` упала, не появляется ни строки `t_users`, ни `t_auth`, ни `t_sessions`, запись о
  повторе не создаётся, а клиент получает ошибку, после которой запрос можно повторить `[hz-02]`.
- Два запроса `verify` с одинаковыми `challengeId` и `code`, отправленные не дожидаясь ответа на первый, оба отвечают
  200 с одним и тем же `session.id`, а в `auth.t_sessions` лежит ровно одна строка `[hz-02/hz-08]`.
- `verify` с верным `challengeId`, но неверным `code` тратит попытку только у этого challenge — счётчики других
  challenge не трогаются `[hz-05]`.
- Запись о повторе не живёт дольше самого кода: её TTL равен `min(окно повтора, время до expiresAt)`. Повтор после
  `expiresAt` получает отказ, даже если успешная проверка прошла за секунду до этого `[hz-01/hz-07]`.
- При недоступном Redis `verify` не выдаёт сессию, а `start` не создаёт challenge. Ни при каких условиях недоступность
  Redis не приводит к приёму непроверенного кода `[hz-02/hz-05]`.
- Погашенный challenge не воскресает при перезапуске Redis: запись, удалённая успешным `verify`, не возвращается, и
  повторный `verify` тем же кодом после рестарта не выдаёт вторую сессию. Отдельная гарантия, а не следствие правила
  про недоступный Redis: то покрывает отсутствующее хранилище, это — хранилище, вернувшееся в устаревшем состоянии
  `[hz-02/hz-04]`.
- Живой challenge не вытесняется под давлением памяти: на Redis с искусственно малым `maxmemory` запись, созданная до
  исчерпания памяти, по-прежнему проходит `verify` и выдаёт сессию, а `start`, которому не хватило места, отвечает
  явной ошибкой вместо молчаливого вытеснения чужой записи `[hz-04/hz-06]`.
- У вызовов SMTP и Redis есть конечные таймауты подключения и чтения (`MAIL_TIMEOUT_SECONDS`); внутри HTTP-запроса
  SMTP не дёргается вообще `[hz-02/hz-06]`.
- Серия отправок, упавших по таймауту, не течёт соединениями: следующая строка очереди всё равно доставляется
  `[hz-06]`.

**Очередь писем**

- Два инстанса воркера, разбирающие очередь одновременно, дают одно письмо на строку, а не два: забор идёт через
  `SELECT ... FOR UPDATE SKIP LOCKED` `[hz-03/hz-08]`.
- Воркер, убитый в состоянии `PROCESS`, не хоронит письмо: через `OUTBOX_PROCESS_TIMEOUT_SECONDS` строка возвращается
  в `ACTIVE` и уходит следующим заходом `[hz-02/hz-04]`.
- Отказ SMTP не терминален: `attempts` растёт, строка возвращается в `ACTIVE`, письмо уходит с той попытки, на которой
  SMTP ожил. После `OUTBOX_MAX_ATTEMPTS` строка становится `FAILED` и больше не берётся — бесконечного цикла
  ретраев нет `[hz-04]`.
- Строка старше `CHALLENGE_TTL_SECONDS` уходит в `FAILED` без попытки отправки: письмо с уже неработающим кодом не
  отправляется никогда `[hz-01/hz-04]`.
- При переходе в `COMPLETED` или `FAILED` ключ `variables` в `data` затирается: в таблице не остаётся ни одного
  открытого кода входа, и его нет в дампах и бэкапах `[hz-07]`.
- Чистка удаляет только `COMPLETED` и `FAILED` старше `OUTBOX_RETENTION_HOURS`. Строка в `ACTIVE` или `PROCESS` не
  удаляется ни при каком возрасте `[hz-04]`.
- Недоступность SMTP не мешает `start` ответить 200 и не оставляет мусора: строка лежит в `ACTIVE` и ждёт `[hz-02]`.
- Модуль авторизации не импортирует ни отправителя писем, ни воркер: единственный его след в подсистеме уведомлений —
  вставка строки. Проверяется тестом на зависимости, а не на глаз `[hz-04]`.

**Жизненный цикл и область действия**

- Счётчик неудачных попыток привязан к `challengeId`, а не к email: новый challenge начинается с нуля, даже если
  предыдущий был исчерпан `[hz-04]`.
- Кулдаун снимается сам: как только прошло `CHALLENGE_RESEND_COOLDOWN_SECONDS`, следующий `start` принимается и шлёт
  код. Отклонённый по кулдауну `start` не продлевает кулдаун `[hz-04]`.
- Любое терминальное состояние (погашен, истёк, исчерпан, вытеснен) отказывает без побочных эффектов: ноль строк в
  `t_sessions`, ноль в `t_users`, ни одного токена в ответе `[hz-04]`.
- `start`, отклонённый валидацией или кулдауном, не удаляет ни одного challenge `[hz-04]`.
- Удаление предыдущего challenge — это удаление по ключу, а не перебор ключей Redis: живой challenge другого email
  выживает, а число операций Redis в `start` не зависит от того, сколько challenge сейчас хранится `[hz-04/hz-06]`.
- Запись challenge с лишним незнакомым полем читается нормально; нечитаемая запись отказывает, а не выдаёт сессию
  `[hz-04]`.
- Уникальность `auth.t_auth` — по паре `(provider, provider_id)`. Удаление строки `t_users` не оставляет висящих строк
  в `t_auth` и `t_sessions` `[hz-04]`.

**Границы и вход**

- Серверные поля, присланные в теле запроса (`challengeId`, `expiresAt`, `code`, `status`, `userId`, `name`,
  `provider`), игнорируются: используется то, что сгенерировал сервер `[hz-05]`.
- Отсутствующие, `null` и `""` значения `challengeType` и `code` отклоняются. `challengeType` не подставляется
  автоматически, даже если в перечислении сейчас всего одно значение `[hz-05]`.
- Email с `\r\n` внутри не подделывает заголовки SMTP и строки лога, не пересекается по ключу Redis с другим email и
  доходит до хранилища как есть `[hz-05/hz-07]`.
- `challengeType`, который прошёл валидацию, но не имеет зарегистрированной стратегии, отклоняется явной ошибкой, а не
  уходит в ветку по умолчанию `[hz-05]`.
- `verify` по несуществующему `challengeId` отвечает ровно так же, как по истёкшему: тот же статус, код и сообщение —
  иначе по ответу можно узнать, существует ли challenge `[hz-05]`.

**Время, конфигурация и утечки данных**

- Время жизни проходит цепочку конфигурация → TTL в Redis → `expiresAt` → `exp` в JWT без искажений: `verify` успешен
  непосредственно до `expiresAt` и отказывает сразу после, а `exp` равен моменту выдачи плюс `ACCESS_TOKEN_TTL_SECONDS`.
  Проверяется на фиксированных часах и на такой длительности, чтобы ошибка в 60 раз (секунды вместо минут) была видна
  `[hz-01/hz-07]`.
- Отказ по кулдауну возвращает остаток ожидания целыми секундами; граница проверяется в трёх точках — за 0,1 с до
  конца кулдауна, ровно в конце и через 0,1 с после `[hz-01/hz-07/hz-08]`.
- Значения по умолчанию в поставке совпадают с таблицей Configuration `[hz-07]`.
- Фактическая конфигурация Redis совпадает с объявленной: `CONFIG GET appendonly` возвращает `yes`,
  `CONFIG GET maxmemory-policy` — `noeviction`. Утверждение читает запущенный сервис, а не файл в репозитории, иначе
  правка флагов в compose разойдётся со спецификацией молча `[hz-07]`.
- Приложение не стартует, если секрет JWT, подключение к Redis или настройки SMTP отсутствуют или пусты — и называет
  недостающую переменную. Закоммиченного рабочего секрета по умолчанию нет `[hz-07/hz-05]`.
- Код из письма, секрет подписи и refresh-токен не появляются ни в одном теле ответа, ни в одной ошибке и ни в одной
  строке лога. Email в логах маскируется `[hz-07]`.
- В телах ошибок нет стектрейсов, SQL, имён ограничений БД, имён классов и путей к файлам. Подробности уходят в лог под
  идентификатором корреляции, который клиент может назвать в поддержке `[hz-07]`.
- Проглоченная гонка при авторегистрации даёт ровно одну запись в логе с указанием `challengeId`, а исчерпавшая
  попытки строка очереди — ровно одну с указанием `id` строки outbox (`challengeId` воркеру неизвестен и знать его ему
  незачем). На счастливом пути таких записей нет `[hz-07]`.
- Ни одна запись лога воркера не содержит `variables`: диагностика печатает `id`, `type`, `attempts` и `last_error`,
  но не код `[hz-07]`.
- Сравнение кода не обрывается на первой несовпавшей цифре `[hz-07]`.

## Validation Rules

| Поле            | Правило                                                                                                                                                                                                                |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `email`         | обязателен, не null, не пустой; ≤ 254 **октетов** — длина проверяется до формата; корректный адрес по RFC; нормализуется (NFC + нижний регистр без учёта локали) перед использованием как ключ, хранением и сравнением |
| `challengeType` | обязателен, не null, не пустой; одно из `EMAIL_CODE`; отсутствующее значение не подставляется                                                                                                                          |
| `challengeId`   | обязателен, UUID                                                                                                                                                                                                       |
| `code`          | обязателен, ровно 6 ASCII-цифр (`U+0030`–`U+0039`); другие виды цифр отклоняются                                                                                                                                       |

## Challenge States

`ACTIVE` (создан, не истёк, попытки остались) переходит в:

- `CONSUMED` — код совпал: challenge удалён, вместо него лежит запись о повторе;
- `EXPIRED` — истёк `CHALLENGE_TTL_SECONDS`;
- `EXHAUSTED` — израсходованы `CHALLENGE_MAX_ATTEMPTS`, challenge удалён;
- `SUPERSEDED` — убит новым `start` для того же ключа.

Сессию выдаёт только `ACTIVE`. `CONSUMED` на верный код отвечает уже выданной сессией, пока жива запись о повторе, а
дальше ведёт себя как `EXPIRED`. Несуществующий `challengeId` отвечает ровно как `EXPIRED`. `SUPERSEDED` возможен
только вместе с сохранённым преемником: `start`, упавший до отправки письма, откатывает всё целиком.

## Core Requirements

- Четыре ключа Redis, каждый читается напрямую — перебора ключей нет нигде:
  - `challenge:{challengeId}` — сама запись: код, счётчик попыток, `expiresAt`, `challengeType`, ключ уникальности.
    TTL ключа равен времени жизни; `expiresAt` хранится в записи, а не вычисляется из остатка TTL.
  - `challenge:key:{challengeType}:{uniquenessKey}` — указатель на живой `challengeId`, чтобы `start` знал, что убить,
    без перебора, а `verify` вообще не нуждался в ключе уникальности.
  - `challenge:cooldown:{challengeType}:{uniquenessKey}` — заявка на повторную отправку.
  - `challenge:verified:{challengeId}` — запись о повторе: хеш кода, выданные `session.id` и `user.id`. Токена в ней
    нет: повтор перечитывает строку сессии и подписывает свежий access-JWT.
- Связка «сравнить код — увеличить счётчик — удалить» в `verify` выполняется одной атомарной операцией Redis. Захват
  кулдауна — одна атомарная установка-если-нет-со-сроком. Обмен «убить предыдущий, сохранить новый» — одна атомарная
  операция над записью и её указателем.
- TTL записи о повторе = `min(CHALLENGE_REPLAY_WINDOW_SECONDS, время до expiresAt)`, поэтому код никогда не работает
  дольше того `expiresAt`, который получил клиент.
- Challenge читается из основного Redis — не из реплики и не из кеша в памяти процесса.
- Redis настроен как долговечное хранилище, а не как кеш: `appendonly yes` с `appendfsync everysec` и
  `maxmemory-policy noeviction`. Восстановление после рестарта идёт из AOF; периодический RDB-снапшот механизмом
  восстановления не является — он отстаёт от реальности и способен вернуть к жизни challenge, удалённый успешным
  `verify`, то есть выдать по одному коду вторую сессию. `noeviction` запрещает Redis выбрасывать живой challenge под
  давлением памяти: переполнение обязано ломать `start` явной ошибкой, а не молча оставлять человека с кодом, записи
  для которого больше нет. Из двух значений дефолт образа даёт только второе (`appendonly` по умолчанию `no`), и
  закрепляются оба — чтобы позднейшая экономия памяти не сняла ни одно из них незаметно.
- Ключ уникальности принадлежит стратегии, и предыдущий challenge убивается **после** выбора стратегии: `TG` и `OAUTH`
  будут ключеваться не по email.
- `verify` гасит challenge до работы с БД. Упавшая транзакция тем самым тратит код — это осознанный выбор, он объявлен,
  а не обойдён.
- Три вставки в `verify` (`t_users`, `t_auth`, `t_sessions`) — одна транзакция.
- Очередь писем — таблица `notifications.t_outbox` в отдельной схеме: `id` (UUID, PK), `type`, `status`, `data`
  (jsonb), `attempts`, `last_error`, `created_at`, `updated_at`. Внешних ключей на `auth` нет, `user_id` нет — на
  момент `start` пользователя ещё не существует, а получатель лежит в `data.to`.
- Модуль авторизации знает об уведомлениях ровно один порт — «положить заявку в очередь». Ни SMTP-отправителя, ни
  шаблонов, ни воркера он не видит; модуль уведомлений, в свою очередь, ничего не знает про challenge.
- Воркер живёт внутри того же приложения (модульный монолит), а не отдельным процессом. Инстансов приложения
  несколько, поэтому забор строк обязан быть конкурентно-безопасным: `SELECT ... FOR UPDATE SKIP LOCKED`.
- Чистка очереди — регулярная задача `pg_cron` в самой БД. Расширения нет в образе `postgres:16`: нужен свой образ с
  `postgresql-16-cron` и прописанным `shared_preload_libraries`, и это отдельный инфраструктурный сценарий, гейтящий
  чистку (но не отправку).
- Счётчик попыток, кулдаун и состояние challenge живут только в Redis: бэкенд работает в нескольких экземплярах и
  ничего не держит в памяти.
- Идентификаторы в `auth` — UUID: `t_users.id`, `t_auth.id`, `t_sessions.id` и внешние ключи на них. Уникальность
  `t_auth` переезжает на `(provider, provider_id)`; у `t_sessions` появляется явный `expires_at`. Обе таблицы получают
  `ON DELETE CASCADE` от `t_users`.
- `auth.t_users.name` при авторегистрации заполняется пустой строкой; строки профиля и онбординга не создаются.
- Access-токен: JWT HS256, `sub=user.id`, `sid=session.id`, срок `ACCESS_TOKEN_TTL_SECONDS`, секрет из конфигурации,
  рабочего значения по умолчанию в репозитории нет.
- Refresh-токен: непрозрачное случайное значение в `auth.t_sessions.refresh_token`, срок `REFRESH_TOKEN_TTL_SECONDS`,
  записан в `expires_at`.
- У пользователя может быть несколько активных сессий: `verify` всегда вставляет новую строку.
- Каждая длительность приходит из конфигурации и читается через внедряемые часы, поэтому границы истечения проверяются
  тестами без реального ожидания.
