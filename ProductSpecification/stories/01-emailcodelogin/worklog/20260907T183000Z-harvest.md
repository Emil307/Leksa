## Найденные дефекты (заведены как красные сценарии)

1. **500 вместо 401 (2.5, 5.3, 5.4, часть SEC 1.1).** `VerifyAuthChallengeService._strategy_for` читает `stored.challenge_type` без проверки на `None`, а `find_challenge` возвращает `None` для всех терминальных состояний.
2. **Запись о повторе не читается (6.1, 7.2).** `find_verification` реализован в `adapter_cache/verification_store.py`, но из production-кода не вызывается — `verify` только пишет через `_remember`.
3. **Гонка регистрации без защиты (7.3).** `session_issuance._link_user`/`_resolve_user` делают read-then-insert без `ON CONFLICT` и без блокировки против `uq_t_auth_provider_provider_id`.
4. **Последняя попытка теряется (5.5).** `CLAIM_ATTEMPT_TEMPLATE` считает попытку номер `max_attempts` израсходованной и удаляет запись до сравнения кода — фактически доступных попыток `max_attempts - 1`.
5. **Рабочие defaults в поставке (INFRA 4.1).** `REDIS_HOST`, `AUTH_CHALLENGE_MAX_ATTEMPTS`, `AUTH_CHALLENGE_TTL_SECONDS`, `AUTH_CHALLENGE_RESEND_COOLDOWN_SECONDS` имеют рабочие значения по умолчанию; `MAIL_TEMPLATE_NAMESPACE` не существует.

## Правки инфраструктуры

## Замечания для будущих циклов

- `infrastructure/scripts/test-acceptance.sh` жёстко подставляет `acceptance/` перед аргументами, поэтому путь не сужает прогон — сужать только `-k`.
- `MalformedChallengeStartStatements._start()` собирает тело запроса сам, потому что типизированный `AuthClient.start_challenge(...)` не умеет выразить «поля нет». Кандидат на `AuthClient.start_challenge_with_raw_body(body)` в `/refactor`.
- 4.5 идёт ~61 с, 8.4 ~181 с — оба честно ждут 60-секундный кулдаун. Профиль конфигурации с низким кулдауном ускорил бы их без правки тестов.
- Цикл ожидания кулдауна продублирован между `SecondLoginStatements` и `EmailSpellingIdentityStatements` — кандидат на извлечение.
- 8.1: клауза «проверка сразу после момента истечения отклоняется» не покрыта и не покрывается на acceptance без управления часами; соседний `test_expired_and_unknown_challenge_acceptance.py` закрывает реально истёкший challenge.
- 7.1 синхронизируется на стороне клиента (`asyncio.Event` + `gather`) — доказывает наблюдаемый исход гонки, но не перекрытие серверных окон; настоящее чередование — в `backend/adapters/cache/tests/test_redis_challenge_store.py`.
- SEC 1.4: две клаузы про лог не проверяются напрямую (бэкенд под uvicorn без файла лога) — заменены наблюдаемыми суррогатами через outbox.
- SEC 1.3 намеренно оставляет строку в outbox и живой challenge — эта строка и есть свидетельство, что фрагмент сохранён как данные.
