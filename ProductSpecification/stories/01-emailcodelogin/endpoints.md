# EmailCodeLogin — эндпоинты API

| Метод | Путь | Описание |
|--------|------|-------------|
| POST | /api/v1/auth/challenge/start | Создать challenge для входа и отправить 6-значный код письмом |
| POST | /api/v1/auth/challenge/verify | Проверить код, при необходимости зарегистрировать пользователя, выдать сессию |

Спецификации: `ProductSpecification/api-specs/auth_challenge_start.yaml`,
`ProductSpecification/api-specs/auth_challenge_verify.yaml`.

## Таксономия ошибок

Любой отказ использует уже отгруженный конверт `{code, message, payload}` из
`adapter_rest/exception_handlers.py` — никаких новых механизмов ошибок (`interview.md`,
раздел «Already Implemented»). Статусы берутся из существующей таблицы `STATUS_BY_CODE`.

| Эндпоинт | Условие | HTTP | code |
|---|---|---|---|
| start | email пустой / длиннее 254 октетов / не адрес; `challengeType` отсутствует, null, пустой или вне перечисления | 400 | `VALIDATION_FAILED` |
| start | кулдаун повторной отправки ещё взведён | 409 | `CONFLICT` |
| start | недоступно хранилище challenge или не удалось поставить письмо в очередь | 503 | `UNAVAILABLE` |
| verify | `challengeId` не UUID; `code` не ровно из 6 ASCII-цифр | 400 | `VALIDATION_FAILED` |
| verify | неверный код · истёк · неизвестен · исчерпан · вытеснен новым | 401 | `UNAUTHORIZED` |
| verify | отказало хранилище challenge или транзакция базы данных | 503 | `UNAVAILABLE` |

`UNAUTHORIZED` различается **сообщением**, а не кодом: «неверный код», «истёк или
неизвестен» и «попытки исчерпаны» несут каждый своё сообщение, причём **у истёкшего и
неизвестного оно одно и то же** — иначе по эндпоинту можно было бы узнать, существует ли
challenge. Остаток попыток наружу не отдаётся никогда.

## Заметки

- **Префикс с версией.** `interview.md` зафиксировал тела запросов и ответов, а точные пути
  делегировал этой фазе («Точные пути и схемы закрепит `/api-spec`»), поэтому путь из
  интервью `/auth/challenge/*` получает предписанный фреймворком префикс `/api/v1/`.
  Отгруженный `/health` остаётся без версии — это инфраструктура, а не функциональный API.
- **`start` отвечает 200 до того, как письмо ушло.** Отправка идёт через outbox: запрос кладёт заявку в
  `notifications.t_outbox`, а письмо отправляет фоновый воркер. Поэтому недоступный SMTP больше не даёт 503 — он
  вообще не виден на границе API. `503` на `start` теперь означает только одно: заявку не удалось принять (лежит
  Redis или Postgres). Следствие для acceptance-тестов: письмо в MailHog появляется не мгновенно, читать его нужно
  с ожиданием, а не сразу после ответа.
- **Два эндпоинта, больше ни одного.** Нет повторной отправки, нет «узнать состояние
  challenge», нет логаута, нет обновления токена. `authorizeUrl` и `status` — явные не-цели
  до появления OAUTH и TG, и в ответе `start` они именно отсутствуют, а не приходят пустыми.
  Будущие провайдеры также используют эти challenge endpoints: отдельного
  `/api/v1/auth/telegram/exchange` не будет. Это решение зафиксировано в
  [ADR границы клиентов](../../tasks/1-refactoring-bot-api-boundary/decisions/unified-client-auth-decision.md).
- **Неизвестные свойства запроса игнорируются, а не отвергаются.** Серверные поля,
  присланные в теле (`challengeId`, `expiresAt`, `code`, `status`, `userId`, `name`,
  `provider`), на результат не влияют; побеждает значение, сгенерированное сервером. Поэтому
  обе схемы запроса объявлены как `additionalProperties: true`.
- **Кулдаун отвечает 409, а не 429.** `CONFLICT` — ближайший член уже отгруженного
  перечисления `ErrorCode`, а завести член `TOO_MANY_REQUESTS` означало бы править продовую
  таблицу `STATUS_BY_CODE` из фазы спецификации. Остаток ожидания едет в
  `payload.retryAfterSeconds` целыми секундами. Стоит пересмотреть, когда появятся лимиты по
  IP, — здесь они объявлены не-целью.
- **`verify` идемпотентен внутри окна повтора.** Повтор того же `challengeId` + `code`
  отвечает 200 с тем же самым `session.id` и `refreshToken` и заново подписанным
  `accessToken`; после окна (по умолчанию 60 с, но не дольше, чем осталось до `expiresAt`)
  отвечает 401 ровно так же, как истёкший challenge.
- **Чтение текущего состояния.** В acceptance-сьюте ровно один включённый тест
  (`TestHealthAcceptance`); эндпоинтов авторизации пока нет. Проверено по
  `backend/adapters/rest/src/adapter_rest/routers/` — `health.py` там единственный роутер.
