# Story 05 — SessionRenewal: контекст интервью

Пользователь продолжает работу без повторного входа: клиент обменивает
действующий refresh-токен на новую пару refresh-токен + access-токен.

## Scope

**В скоупе:**

- `POST /api/v1/auth/token/refresh` принимает refresh-токен и обновляет
  существующую сессию.
- При каждом успешном обновлении refresh-токен ротируется.
- Новый access-токен можно получить в любой момент, пока refresh-токен
  действителен: ждать истечения текущего access-токена не нужно.
- Истёкший, неизвестный и уже использованный refresh-токен отклоняются.
- Два одновременных запроса с одним refresh-токеном дают ровно один успешный
  результат.
- Ошибка хранилища не должна частично погасить действующий refresh-токен.

**Вне скоупа:**

- logout;
- управление устройствами и списком сессий;
- хранение токенов в cookie и другая клиентская политика хранения;
- проверка access-токена на защищённых ручках (`AccessTokenGuard`);
- rate limiting;
- клиентская логика повторов и координация обновления между вкладками.

## API Endpoint

| Метод | Путь | Статус |
|---|---|---|
| POST | `/api/v1/auth/token/refresh` | NOT YET IMPLEMENTED |

**Request:**

```json
{ "refreshToken": "string" }
```

**Response:**

```json
{
  "session": {
    "id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
    "refreshToken": "string",
    "accessToken": "string"
  }
}
```

DECISION: объект `user` в ответе не повторяется. Успешная ротация сохраняет
существующий `session.id` и не создаёт новую сессию.

## Token / Auth Requirements

Базовый формат токенов и сессии принадлежит `EmailCodeLogin`: access-токен —
JWT HS256 с `sub`, `sid`, `exp`; refresh-токен — случайное непрозрачное значение,
а источником правды служит строка сессии в PostgreSQL. Эта история не меняет эти
решения.

DECISION: для обновления достаточно refresh-токена. Действующий или истёкший
access-токен передавать не требуется.

DECISION: срок refresh-токена скользящий. После каждой успешной ротации новая
дата окончания равна моменту ротации плюс настроенный срок жизни refresh-токена.

DECISION: новый access-токен относится к тому же пользователю и той же сессии,
что и предъявленный refresh-токен.

## Key Architectural Decisions

DECISION: ротация атомарная. Один запрос одновременно проверяет действительность
предъявленного refresh-токена, заменяет его и продлевает срок сессии. Частично
применённого результата быть не должно.

DECISION: если два запроса одновременно предъявили один refresh-токен, ровно
один из них ротирует токен и получает новую пару. Второй получает `401
Unauthorized`.

DECISION: повтор уже использованного refresh-токена не отзывает новую пару,
выпущенную успешным запросом. Он обрабатывается так же, как неизвестный токен.

DECISION: если PostgreSQL недоступен или транзакция не завершилась, клиент
получает серверную ошибку, а старый refresh-токен остаётся действительным.

## Business Rules & Constraints

- Истёкший, неизвестный и уже использованный refresh-токен отвечают одинаковым
  `401 Unauthorized`, без раскрытия причины отказа.
- Успешный ответ всегда содержит новый refresh-токен и заново выпущенный
  access-токен.
- Старый refresh-токен перестаёт действовать сразу после успешной ротации.
- Обновление разрешено до истечения текущего access-токена.
- Потеря успешного ответа не даёт права повторно использовать старый
  refresh-токен: повтор получит `401`, поскольку токен строго одноразовый.
- Несколько сессий одного пользователя независимы: обновление одной не меняет
  токены и сроки остальных.

## Already Implemented / REUSE

- Контракт сессии, время жизни и формат токенов определены в истории
  `EmailCodeLogin`; здесь они переиспользуются, а не проектируются заново.
- Централизованные доменные ошибки и REST-обработчики уже существуют и должны
  остаться единым механизмом ошибок.
- `UnitOfWork` и базовый SQLAlchemy-репозиторий уже доступны для атомарной
  операции с хранилищем.

**Текущее состояние продукта:** включённые acceptance-тесты описывают только
`/health`. Реализация пользователей, сессий и токенов ещё создаётся в
`EmailCodeLogin`; готового refresh endpoint в коде нет.

## NOT Yet Implemented

- usecase ротации токенов;
- атомарная операция поиска и замены refresh-токена в хранилище;
- REST-контракт `/api/v1/auth/token/refresh`;
- выпуск нового access-токена для существующей сессии;
- обработка истёкшего, неизвестного и повторно использованного токена;
- конкурентная гарантия «ровно один успешный запрос»;
- acceptance- и модульные тесты обновления сессии.

## Cross-Story Dependencies

- История зависит от `EmailCodeLogin`: сначала должны существовать пользователь,
  строка сессии, выпуск токенов и их конфигурация.
- `AccessTokenGuard` не блокирует эту историю: refresh endpoint работает только
  по refresh-токену.
- Logout и управление сессиями используют тот же жизненный цикл сессии, но
  остаются отдельными будущими историями.

## Testing Considerations

- Проверить успешную ротацию до и после истечения прежнего access-токена.
- Проверить скользящий срок refresh-токена управляемыми часами, без ожидания года.
- Проверить одинаковый внешний ответ для истёкшего, неизвестного и уже
  использованного refresh-токена.
- Отправить два конкурентных запроса с одним токеном: один успешен, второй
  получает `401`, а в хранилище остаётся одна новая пара для той же сессии.
- Имитировать отказ хранилища до завершения транзакции и доказать, что старый
  refresh-токен не погашен.
- Проверить, что ротация одной сессии не меняет другую сессию пользователя.

## Performance / Rate Limits

`ProductSpecification/ExpectedLoad.md` пока не содержит чисел нагрузки. Отдельный
rate limiting в эту историю не входит. Приложение работает в нескольких
инстансах, поэтому конкурентная гарантия обеспечивается общей базой данных, а не
in-memory состоянием процесса.
