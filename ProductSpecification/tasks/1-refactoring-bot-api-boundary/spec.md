# Task 1: Граница API и бота

Type: refactoring

## Problem

Telegram-бот был разработан до подключения framework как самостоятельное
приложение с собственной продуктовой моделью, PostgreSQL, Alembic, репозиториями
и application services. Из-за этого бот одновременно является Telegram-интерфейсом
и вторым backend: он хранит пользователей, учебный контент, игровые сессии,
результаты, подписки и рефералы, а часть поведения реализована заглушками.

Такая граница мешает развивать один продукт через несколько клиентов. API,
frontend и Telegram-бот могут начать по-разному трактовать одни и те же правила,
а изменения продукта приходится дублировать. Сейчас основной API содержит только
базовый каркас и health check, поэтому удалить продуктовые слои из бота одним
изолированным изменением без предварительного проектирования контрактов нельзя.

## Solution

Целевое состояние: Telegram-бот становится независимо разворачиваемым клиентом
единого HTTP API, аналогично frontend-приложению. Бот не импортирует backend-код,
не подключается к продуктовой базе данных и не вычисляет авторитетные продуктовые
результаты.

API является единственным владельцем:

- пользователей, учетных записей и привязок внешних способов входа;
- аутентификации, авторизации, подписок и рефералов;
- учебного и игрового контента;
- игровых сессий, результатов, статистики и их постоянного хранения;
- проверки присланных клиентом ответов и итоговых вычислений.

API знает о Telegram только как о стратегии общего challenge lifecycle. Все способы
входа используют `/api/v1/auth/challenge/start` и
`/api/v1/auth/challenge/verify`; отдельного `/api/v1/auth/telegram/exchange` нет.
API не должен знать про Telegram handlers, callback data, клавиатуры, сообщения,
изображения, forum topics или шаги диалога. Telegram challenge обязан проверить
bot client и provider-specific evidence до выдачи общей пользовательской сессии.
Полное решение зафиксировано в
[ADR аутентификации](decisions/unified-client-auth-decision.md).

Бот остается владельцем только Telegram-специфичного поведения:

- webhook/polling транспорта, handlers и middleware;
- callback data, клавиатур, текстов, медиа и форматирования сообщений;
- FSM диалога и Telegram message/thread identifiers;
- временного пользовательского ввода и повторов запросов;
- Telegram `file_id` cache и управления forum topics.

Redis разрешен как временное хранилище состояния интерфейса с TTL: текущий шаг
FSM, идентификатор API-сессии или игровой сессии, Telegram identifiers, временный
ввод и `file_id`. Redis и память бота не становятся источником продуктовой истины.
После миграции из бота удаляются SQLAlchemy, Alembic, PostgreSQL, продуктовые
repositories, их persistence models и дублирующие продуктовые domain entities и
services. Telegram-специфичный `GameThreadService` сохраняется, но его постоянное
хранилище заменяется временным Redis-хранилищем.

Игровой поток использует два API-запроса:

1. `POST /games/{type}/sessions` создает фиксированный snapshot сессии и возвращает
   `session_id`, срок действия, весь набор вопросов, варианты, правильные ответы,
   пояснения и необходимые медиа.
2. `POST /games/sessions/{id}/complete` принимает фактически выбранные ответы.
   API повторно вычисляет результат по сохраненному snapshot, сохраняет ответы,
   результат и статистику, затем возвращает авторитетный итог.

Бот хранит snapshot только на время игры, сам ведет Telegram-диалог, сразу
показывает обратную связь и может считать предварительный результат. Переданный
ботом score не считается достоверным. Завершение сессии идемпотентно: повтор с
теми же ответами возвращает тот же результат, а повтор с другим набором ответов
отклоняется как конфликт. Сессии имеют срок действия; незавершенную отправку можно
временно сохранить в Redis для повтора. Правильные ответы допустимо отдавать
клиенту, потому что результаты влияют только на статистику, а не на оплату,
доступ, награды или иные защищаемые права.

Миграция должна сохранять работоспособность пользовательских потоков по мере
переноса ответственности. Заглушки текущего бота — безусловно успешная проверка
подписки на канал, активация подписки без оплаты, принятие любого непустого
промокода, фиктивная подарочная подписка, заглушки кабинета и карточной игры — не
считаются продуктовым поведением и не переносятся в API без отдельных историй.

Точные API-контракты, последовательность вертикальных срезов и границы отдельных
продуктовых историй определяются на стадиях `design` и `refactor (steps discovery)`.
Тесты не создаются до утверждения дизайна и удаления неоднозначности в зонах
ответственности.
