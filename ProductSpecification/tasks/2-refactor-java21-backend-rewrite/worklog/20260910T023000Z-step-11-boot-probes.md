# Step 11: boot-пробы acceptance-набора на JVM

## Что сделано

- Новый `acceptance/statements/jvm_configuration_probe.py`: запускает boot-jar через
  `java -Dloader.main=com.uwords.application.ConfigurationProbe -cp <jar>
  org.springframework.boot.loader.launch.PropertiesLauncher`, наследует только `PATH`, `HOME`,
  `JAVA_HOME`, остальные переменные приходят из сценария. Таймаут 90 секунд. Если boot-jar не собран,
  падает с внятным сообщением про `./gradlew :backend:application:bootJar`.
- `configuration_startup_statements.py`: `_start` больше не запускает `python -c "import
  application.main"`, а вызывает пробник; остальные методы и константы не изменились.
- `signing_secret_boot_statements.py`: переписан на тот же пробник, `BootAttempt` заменён на общий
  `ProbeResult`. Сигнатуры given/when/assert сохранены -- тест не менялся.
- Сами acceptance-тесты не тронуты (правка теста в этой задаче запрещена).

## Правка продакшн-кода: имя переменной окружения в отказе

Тест требует, чтобы в диагностике стартового отказа стояло имя переменной (`JWT_SECRET`), а не имя
свойства. Spring в `BindValidationException` называет `auth.token.jwtSecret`. Добавлен
`com.uwords.application.ConfigurationRefusal`: по полям `BindValidationException` восстанавливает путь
свойства (`auth.token` + kebab-case поля), ищет его **неразрешённое** значение в property source
`application.yml` и достаёт имя переменной из плейсхолдера `${...}`. `ConfigurationProbe` теперь
передаёт собственный `StandardEnvironment` в `SpringApplicationBuilder`, чтобы источники свойств
остались доступны после провала refresh.

Так связь «свойство -> переменная окружения» не дублируется в коде: единственный её источник --
`application.yml`.
